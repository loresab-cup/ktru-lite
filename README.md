# КТРУ-классификатор

Сайт для кейс-чемпионата B2B-РТС (задача 5). Пользователь загружает спецификацию закупки
(xlsx, csv, docx, pdf или txt). Система достаёт из каждой строки наименование, бренд, модель и
характеристики, подбирает код каталога КТРУ и считает уверенность в процентах. Спорные позиции
человек проверяет и при необходимости правит, потом выгружает результат в xlsx или csv.

Этот файл написан для того, кто будет разбираться в коде. Сначала общая картина, потом каждый
модуль по отдельности, потом рецепты для типовых правок. Прежний README с историей решений и
замерами лежит в [docs/notes-and-measurements.md](docs/notes-and-measurements.md).

## 1. Что внутри, в двух словах

Четыре контейнера в одном `docker-compose.yml`:

- `frontend`: nginx со статикой React и прокси на backend. Порт 3000.
- `backend`: FastAPI на Python 3.12. Принимает файлы, держит очередь заданий, считает коды.
- `db`: PostgreSQL 16. Таблицы `jobs` и `items`.
- `ollama`: сервис эмбеддингов с моделью bge-m3. Превращает текст в вектор из 1024 чисел.

Работа над одной строкой спецификации идёт так:

```
строка файла
   |  parser.py       разбор файла в строки
   v
нейросеть (Gemini, запасной GigaChat) достаёт наименование, бренд, модель, характеристики
   |  extractor.py + providers.py
   v
вектор строки (bge-m3)
   |  embedder.py
   v
поиск по каталогу из 81 509 кодов: косинус, BM25, правила ранжирования
   |  search.py
   v
пять кандидатов, уверенность в процентах, статус
   |  confidence.py
   v
спорные строки перепроверяет нейросеть, выбирая из пяти кандидатов
      chooser.py
```

Два момента, которые важно понимать сразу.

Нейросетям не доверяют. Всё, что они вернули (наименование, бренд, значения), проверяется:
значение остаётся, только если оно дословно есть в исходной строке. Если нейросеть недоступна,
атрибуты берутся простыми правилами, и задание всё равно заканчивается.

Код выбирает не нейросеть, а поиск по каталогу. Нейросеть извлекает атрибуты и в конце даёт
второе мнение по спорным строкам, но только из тех пяти кодов, которые уже нашёл поиск.
Придумать несуществующий код она не может.

## 2. Запуск

### Что нужно

- Docker Desktop (на Windows с WSL 2) или Docker Engine с Compose v2.
- Дамп каталога `db/ktru_catalog.jsonl.gz` (около 344 МБ). В git его нет, положите файл в
  папку `db/`. Каталог берётся из справочника организаторов, с сайта ЕИС его не парсили.
- Около 6 ГБ диска и 4 ГБ свободной памяти.
- Интернет при первой сборке (образы, пакеты, модель bge-m3) и для запросов к нейросетям.
- Необязательно: видеокарта NVIDIA. Эмбеддинги на ней в десять раз быстрее.

### Одна команда

```bash
docker compose up -d --build
```

Сайт откроется на http://localhost:3000. Документация API на http://localhost:8000/api/docs
доступна только с этого компьютера. Первая сборка занимает 5-10 минут. Каталог после старта
загружается около 20 секунд, пока идёт загрузка, в шапке написано «Каталог загружается».

Без `.env` всё запустится, но нейросетей не будет: атрибуты извлекаются правилами, точность
ниже. Эмбеддинги в этом случае считаются на процессоре.

### Настройка `.env`

```bash
cp .env.example .env
```

В `.env` нужно вписать:

1. Ключи нейросетей. `LLM_PROVIDERS=gemini,gemini2,gemini3,gemini4,gemini5,gigachat` задаёт
   список и порядок. Для каждого Gemini нужна только строка `GEMINIn_API_KEY`: адрес, модель,
   число потоков и лимит запросов берутся из блока `GEMINI_*`. Для GigaChat нужен
   `GIGACHAT_CREDENTIALS`.
2. Видеокарту, если она есть. Раскомментируйте две строки `COMPOSE_PATH_SEPARATOR` и
   `COMPOSE_FILE`, тогда та же команда запустит Ollama на GPU.

После правки `.env` выполните `docker compose up -d --build` ещё раз. Проверить ключи можно так:

```bash
docker compose exec backend python check_llm.py
```

Каждому провайдеру положено ответить `OK за N с`. Если нет, скрипт подскажет причину: 401 это
ключ, 402 баланс, 404 модель или адрес, 429 слишком много потоков.

### Остановить, перезапустить, сбросить

```bash
docker compose stop              # остановить, данные остаются
docker compose up -d             # запустить снова
docker compose logs -f backend   # лог обработки: какой провайдер, сколько секунд
docker compose down -v           # удалить контейнеры и все данные
```

### Запуск без Docker (для разработки)

Backend (Python 3.12), из папки `backend/`:

```bash
python -m venv .venv
# активируйте окружение (Windows: .venv\Scriptsctivate), затем
pip install -r requirements.txt pytest ruff
export DATABASE_URL=sqlite:///./dev.db
export CATALOG_PATH=../db/ktru_catalog.jsonl.gz
export CACHE_DIR=./.cache
export UPLOAD_DIR=./.uploads
export OLLAMA_URL=http://localhost:11434
uvicorn api:app --reload --port 8000
```

Для разработки хватает SQLite. Если Ollama не запущена, поиск идёт только по словам, точность
ниже. Frontend (Node 24), из папки `frontend/`:

```bash
npm ci
npm run dev      # http://localhost:5173, запросы /api уходят на localhost:8000
```

Можно смешивать: `db`, `ollama` и `backend` в Docker, а интерфейс через `npm run dev`.

## 4. Архитектура

### Контейнеры и порты

```
браузер
   |  http://localhost:3000
   v
frontend (nginx, порт 8080 в контейнере)
   |  /            статика React, любой неизвестный адрес отдаёт index.html
   |  /api/*       прокси на backend:8000
   v
backend (FastAPI)  ----->  db (PostgreSQL)      jobs, items
   |        |
   |        +------------>  ollama               bge-m3, эмбеддинги
   |
   +------------------->  Gemini, GigaChat       внешние нейросети по HTTPS
```

Порты наружу: 3000 (сайт) и 127.0.0.1:8000 (API и документация, только с этого компьютера).
Данные лежат в томах: `pgdata` (база), `cache` (кэш матрицы каталога), `uploads` (загруженные
файлы до конца обработки). Каталог монтируется из `./db` только для чтения.

### Очередь без Redis

Очередью служит таблица `jobs`. При запуске backend поднимает `WORKERS` потоков (по умолчанию 2).
Каждый поток раз в секунду пробует взять задание со статусом `queued`:

```sql
SELECT id FROM jobs WHERE status = 'queued' ORDER BY created_at LIMIT 1
FOR UPDATE SKIP LOCKED
```

После выбора идёт условный `UPDATE ... WHERE status = 'queued'`: если задание успел взять другой
поток, обновится ноль строк, и этот поток пойдёт дальше. Пока файл обрабатывается, число готовых
строк пишется в `jobs.processed`, по нему интерфейс рисует прогресс. Если backend перезапустили
посреди работы, задания со статусом `processing` при старте возвращаются в `queued` и
обрабатываются заново с начала (`init_db`).

### Два вида нейросетей

Внешняя (Gemini, GigaChat) разбирает текст строки на атрибуты. Локальная (bge-m3 в Ollama)
только считает векторы. Вектора каталога уже лежат в дампе, поэтому модель `EMBED_MODEL` должна
совпадать с той, которой считали дамп.

### Каталог в памяти

Весь каталог (81 509 кодов, вектор 1024 float32 у каждого, около 334 МБ) хранится в памяти
backend. Поиск это умножение матрицы запросов на матрицу каталога, то есть точный косинус без
приближений. Приближённый индекс (HNSW) пробовали, он терял до 14 процентов верных кодов.
Первый старт читает дамп и строит матрицу, потом пишет её в `CACHE_DIR`, следующие старты берут
кэш и занимают секунды.

## 5. Путь одного файла

Что происходит от нажатия «Обработать» до выгрузки, по шагам и с названиями функций.

1. Браузер отправляет файл на `POST /api/jobs` (`create_job` в `api.py`). Backend читает не
   больше 10 МБ плюс один байт, проверяет, что файл не пустой и что начало файла соответствует
   расширению (`parser.check_signature`). Файл сохраняется на диск под именем `<uuid>.<ext>`,
   имя пользователя на диск не попадает. В таблицу `jobs` пишется запись со статусом `queued`.
   Ответ 202 с идентификатором задания.
2. Интерфейс переходит на `/jobs/<id>` и раз в секунду спрашивает `GET /api/jobs/<id>`.
3. Свободный воркер берёт задание (`claim_job`) и запускает `run_job`.
4. `parser.parse_file` читает файл и возвращает список `Item(row_number, text, columns)`.
   Строк не больше 1000.
5. Создаётся `extractor.JobExtractor`. Он режет уникальные тексты на пачки по `LLM_BATCH` строк
   (по умолчанию 20) и сразу отдаёт первые пачки в общий пул потоков, не больше двух кругов
   по числу слотов всех провайдеров. Пока одна пачка ждёт ответа, остальные уже летят.
6. `process_items` идёт по строкам файла пачками по 20 (`BATCH` в `api.py`). Для каждой пачки
   `process_batch`:
   - берёт атрибуты у `JobExtractor` (`llm.get`), при необходимости ждёт;
   - собирает запрос для поиска: `search_text` из нейросети плюс исходный текст строки;
   - определяет единицу измерения: из колонки «Ед. изм.» файла и из догадки нейросети;
   - считает векторы (`embedder.embed`) и ищет кандидатов (`Catalog.search`);
   - превращает результат в записи `Item` (`build_item`: код, уверенность, зона, статус,
     пояснение) и пишет их в базу одной транзакцией;
   - обновляет `jobs.processed`.
   Поэтому готовые карточки появляются в интерфейсе по двадцать штук, пока остальные считаются.
7. Когда все строки обработаны, `choose_codes` берёт позиции со статусом `needs_review` и
   отдаёт нейросети на второе мнение (`chooser.choose`). Код меняется, только если нейросеть
   выбрала другой код из тех же пяти кандидатов. Уверенность и статус при этом не трогаются:
   строка всё равно остаётся на проверку человеку.
8. `finish` ставит статус `done`, время этапов (`stage_seconds`) и удаляет загруженный файл.
9. Человек открывает карточки, принимает или исправляет коды. Каждое действие это отдельный
   запрос к `/api/items/...`.
10. «Выгрузить» открывает `GET /api/jobs/<id>/export`, backend собирает xlsx или csv из таблицы
    `items`.

Остановка (`POST /api/jobs/<id>/cancel`) ставит статус `cancelled` и взводит `threading.Event`
этого задания. Очередь пакетов к нейросети снимается, воркер выходит из цикла между пачками.
Уже обработанные позиции остаются, их можно проверить и выгрузить.

## 6. Backend по модулям

### api.py

Самый большой файл (834 строки): модели, очередь и все эндпоинты. Порядок в файле такой.

Настройки в начале: `DATABASE_URL`, `UPLOAD_DIR`, `WORKERS`, `JOB_TIME_LIMIT = 270` секунд (потолок
времени одного задания), `BATCH = 20` (сколько строк пишется в базу за раз), `ITEM_STATUSES`.

Модели `Job` и `Item` описаны в разделе 7.

`State` хранит каталог (`catalog`), флаг ошибки загрузки каталога, событие остановки воркеров
и словарь `cancels`: для каждого идущего задания свой `threading.Event`.

Блок очереди:

- `claim_job`: взять задание из очереди (см. раздел 4).
- `run_job`: основной цикл обработки одного задания. Читает файл, запускает `process_items`,
  потом `choose_codes`, в конце `finish`. Любое исключение превращается в понятный статус
  `failed` с текстом для пользователя. После завершения файл удаляется.
- `process_items` и `process_batch`: пачки по 20 строк, описаны в разделе 5.
- `apply_candidates`: из списка кандидатов выставляет код, название, уверенность, зону, статус и
  пояснение позиции. Её же использует правка атрибутов.
- `build_item`: создаёт `Item`. Если на строке случилась ошибка, позиция получает статус
  `failed`, но задание продолжается.
- `choose_codes`: второе мнение. Меняет код через условный `UPDATE`, который сработает только
  если позиция всё ещё `needs_review` с тем же кодом, так что правки человека во время
  обработки не затираются.
- `finish`: итоговый статус. Остановленное задание остаётся остановленным, даже если воркер
  дописал позже.
- `worker_loop`, `load_catalog`, `init_db`, `lifespan`: запуск и остановка.

Эндпоинты описаны в разделе 8. Некоторые детали, которых нет в таблице:

- `get_job` кроме полей задания отдаёт `counts` (сколько позиций в каждом статусе) и `fallback`
  (у скольких строк атрибуты получены правилами, а не нейросетью).
- `list_jobs` отдаёт те же `counts` для каждого задания одним запросом и общее число заданий в
  заголовке `X-Total-Count`.
- `list_items` умеет фильтровать по статусам через запятую, искать по тексту строки, коду и
  названию (без учёта регистра, спецсимволы `%` и `_` экранируются), и по флагу
  `candidates=false` не отдаёт пять кандидатов. Они нужны только странице позиции, а весят около
  10 КБ на строку.
- `get_item` возвращает позицию и её место в задании: `position`, `total`, `prev_id`, `next_id`,
  `next_unreviewed_id` (следующая позиция, не принятая и не исправленная).
- `correct_item` принимает код с пробелами и переносами, проверяет его по каталогу и ставит
  статус `corrected`, уверенность 100.
- `edit_attributes` принимает исправленные наименование, бренд, модель и характеристики, строит
  новый поисковый запрос, ищет заново и обновляет код. Исходные колонки файла сохраняются.
- `accept_item` и `accept_job`: принять один код или все коды выше порога уверенности. Массово
  принимаются только действующие коды.
- `revert_item` отменяет принятие или ручной код. Для этого перед первым изменением в
  `attributes.original` сохраняется снимок: код, название, уверенность, зона, статус, пояснение.
  `revert` восстанавливает снимок и удаляет его. Если позиция была принята до появления снимков,
  код остаётся, а уверенность, зона и статус пересчитываются по кандидатам.
- `delete_job` удаляет позиции, задание и файл. Задание в обработке удалить нельзя (409).
- Выгрузка: `export_rows` собирает таблицу. К колонкам исходного файла добавляются
  наименование, бренд, модель, характеристики, код, название кода, уверенность, статус кода и
  статус позиции. Функция `cell` ставит апостроф перед текстом, который начинается с `=`, `+`,
  `-` или `@`, чтобы Excel не принял ячейку за формулу. CSV пишется с разделителем `;` и BOM
  (`utf-8-sig`), чтобы Excel открыл кириллицу. Колонка `candidates` при выгрузке из базы не
  читается (`defer`).

### parser.py

Превращает файл в список позиций `Item(row_number, text, columns)`. `text` это строка, которая
пойдёт нейросети и поиску, `columns` все исходные колонки для выгрузки.

Что делает для каждого формата:

- xlsx: читает все листы в режиме `read_only`, проверяет, что внутри не zip-бомба (не больше
  200 МБ после распаковки) и ячеек не больше 300 тысяч.
- csv: кодировка utf-8 или cp1251, разделитель определяется (`;`, `,` или табуляция).
- docx: сначала таблицы, если их нет, то абзацы.
- pdf: текст не больше 200 страниц, каждая строка текста это позиция.
- txt: каждая непустая строка это позиция.

Как найти нужные колонки в таблице (`parse_rows`): сначала ищется строка заголовка среди первых
тридцати (в ней должны быть слова вроде «наименование», «товар», «характеристик», «количество»).
Колонка с наименованием определяется по заголовку, а если его нет, берётся колонка с самым
длинным текстом. Колонки со словами «характеристика», «бренд», «марка», «модель»,
«производитель», «описание» присоединяются к тексту позиции. Служебные колонки (инструкция,
обоснование, национальный режим) в текст не попадают. Пустые строки, «Итого» и строки-повторы
заголовка пропускаются.

Отдельно разобрана форма ЕИС «Описание объекта закупки» (`parse_eis_rows`): там товар занимает
несколько строк таблицы, по одной характеристике на строку, а «№» и наименование заполнены
только в первой. Такие строки склеиваются в одну позицию, единица измерения товара добавляется
в конец текста.

Ограничения (`MAX_*` в начале файла): 10 МБ файл, 1000 позиций, 2000 символов в ячейке. Ошибки,
которые должен исправить пользователь, это `ParseError` с готовым русским текстом.

### extractor.py

Достаёт из текста строки структуру: `name`, `brand`, `model`, `characteristics`
(`name`, `value`, `unit`), `search_text` и `measure` (единица, в которой такой товар обычно
закупают).

Системный промпт (`SYSTEM_PROMPT`) говорит нейросети, что сообщение пользователя это данные, а
не инструкции. Строки уходят JSON-массивом `[{id, text}]`. Это защита от строк, в которых
написано что-то вроде «забудь инструкции».

Главная защита `accept`: значение из ответа принимается только если оно дословно встречается в
исходной строке (после приведения к нижнему регистру, замены `ё` на `е` и сжатия пробелов).
Исключения: `search_text` и `measure` это подсказки для поиска, их по строке не проверяют.
Если наименование нейросети в строке не нашлось, подставляется наименование от правил.

Правила (`rules`) работают без сети. Бренд это латинское слово с заглавной, модель это токен с
цифрами сразу после бренда, наименование это начало строки до первой запятой, цифры или
латинского слова. Характеристики вытаскивает регулярное выражение «название, число, единица».
Причина, по которой пришлось использовать правила, записывается в `attributes.fallback` и
показывается пользователю: `no_key` (нет ключа), `unavailable` (нейросеть не ответила),
`budget` (кончилось время), `error` (ошибка), `missing` (нейросеть пропустила строку).

Как запрос проходит провайдеров (`ask`, `take_provider`):

1. Берётся первый провайдер из списка, у которого есть ключ, он не на паузе и не пробовался
   для этой пачки. GigaChat берётся только когда не осталось ни одного другого: пока Gemini
   просто занят, пачка ждёт его, а не уходит к GigaChat.
2. Если запрос не удался, провайдер получает паузу и пачка уходит следующему. Сетевая ошибка
   без ответа даёт паузу 30 секунд (отказ в соединении 15), 401, 402 и 403 дают 120 секунд,
   429 и 502-504 дают 15 секунд, в течение которых пачки идут к другим.
3. Если ответ обрезан по `max_tokens` (`AnswerCut`), пачка делится пополам и каждая половина
   спрашивается отдельно (`extract_chunk`). Другой провайдер обрезал бы то же самое.
4. Строки, которые модель пропустила в большом ответе, спрашиваются повторно отдельной
   маленькой пачкой.
5. Если все провайдеры не справились или кончился бюджет `LLM_BUDGET` (240 секунд), оставшиеся
   строки получают атрибуты от правил.

`JobExtractor` держит в пуле потоков не больше двух кругов пачек (`AHEAD_ROUNDS`), чтобы другое
задание, загруженное в это время, не ждало весь большой файл. Пул `_pool` общий для всех заданий
и для второго мнения, потоков в нём столько, сколько слотов у всех провайдеров.

### providers.py

Настройки и запрос к одной нейросети.

- `Provider`: имя, тип (`gigachat` или `openai`, то есть любой OpenAI-совместимый API,
  каким пользуется Gemini), адрес, ключ, модель, число одновременных запросов (семафор
  `slots`), лимит запросов в минуту `rpm`, моменты `down_until` и `busy_until` (паузы).
- `load()` читает `LLM_PROVIDERS` и для каждого имени собирает `Provider` из переменных
  окружения. `setting()` для имён, начинающихся с `gemini`, берёт недостающие значения из блока
  `GEMINI_*`, поэтому для нового ключа достаточно одной строки `GEMINIn_API_KEY`.
- `chat()` делает запрос с двумя повторами на 429, 5xx и молчащую сеть. Ответ 5xx, пришедший
  позже 15 секунд, считается молчанием шлюза и повторов не получает.
- `wait_turn()` растягивает запросы провайдера во времени на 60/RPM секунд, чтобы бесплатный
  тариф не отвечал 429.
- GigaChat выдаёт токен на 30 минут через OAuth, он кэшируется (`access_token`) и обновляется
  за минуту до конца. Сертификаты GigaChat выданы российским корневым центром, которого нет в
  обычных хранилищах, поэтому по умолчанию проверка выключена (`GIGACHAT_VERIFY_SSL=false`).
  Её можно оставить включённой, указав путь к файлу `.pem`.
- Температура `0.0001`: так ответы воспроизводимы.

### embedder.py

`embed(texts)` отправляет тексты в Ollama (`POST /api/embed`, модель `bge-m3`) пачками по 64,
четырьмя потоками, и нормирует векторы. Одинаковые тексты спрашиваются один раз и кэшируются
между заданиями (до 50 тысяч записей). Если Ollama недоступна или ответ неверный, функция
возвращает `None`, и поиск работает только по словам.

### search.py

Каталог в памяти и поиск кандидатов. Класс `Catalog` держит матрицу векторов и списки метаданных:
коды, статусы, названия, ОКПД2, слова, характеристики, числовые границы, «неизменяемые
заказчиком» значения, признак «шаблон группы», единицы.

`Catalog.search(vectors, texts, include_inactive, units, column_units)` для каждой строки:

1. Считает косинус с каждым кодом и берёт 50 ближайших (`_nearest_by_vectors`). Недействующие
   коды отбрасываются, если пользователь не включил «Учитывать недействующие коды».
2. Добавляет до 20 кодов по BM25 над основами слов в названии кода (`_lexical`). Код, у которого
   название совпало со строкой, попадёт в кандидаты, даже если вектор был не среди ближайших.
3. Каждому кандидату считает оценку в `_rank`: косинус плюс поправки. Поправки задают
   константы в начале файла.

| Константа | Что делает |
| --- | --- |
| `WORD_BONUS` 0,02 | за каждое слово, общее у строки и кода (числа не считаются) |
| `NUMERIC_BONUS`, `NUMERIC_CLASH` 0,01 | числовые границы строки совпали с границами кода или легли на другую сторону |
| `FIXED_BONUS` 0,02, `FIXED_CLASH` 0,04, `FIXED_FLAG` 0,03 | значения «неизменяемых» характеристик кода написаны в строке, противоречат ей, или у кода есть особое «Да», которого в строке нет |
| `TEMPLATE_PENALTY` 0,015 | общий код-шаблон группы чуть ниже конкретного |
| `NAME_EXTRA_PENALTY` 0,01 | за каждое слово названия кода, которого нет в строке |
| `UNNAMED_PENALTY` 0,02 | за каждую характеристику кода, которую строка не называет |
| `UNIT_BONUS` 0,005, `COLUMN_UNIT_BONUS` 0,03 | единица совпала с догадкой нейросети или с колонкой «Ед. изм.» файла |

4. Сортирует и оставляет пять лучших. Каждый кандидат отдаётся с названием, ОКПД2, статусом,
   характеристиками, оценкой, косинусом, общими словами и совпавшими характеристиками.

Обоснования значений констант записаны комментариями рядом с ними: каждое подбиралось по
замерам. Менять их по одной без замера на двух наборах нельзя, одно улучшение легко портит
другое (подробнее в разделе 16).

`load_catalog` читает дамп (`build`) или кэш из `CACHE_DIR`. Ключ кэша состоит из версии
`CACHE_VERSION`, размера и времени изменения дампа. Если поменяете состав метаданных, поднимите
`CACHE_VERSION`, иначе будет использоваться старый кэш. Метод `lookup` ищет код для ручной
правки: по началу кода или по словам названия, действующие коды первыми.

### confidence.py

Из пяти кандидатов делает уверенность в процентах:

```
z = 11.05 * оценка_первого + 76.0 * (оценка_первого - оценка_второго) - 8.28
уверенность = 100 / (1 + exp(-z))
```

Чем выше оценка первого кандидата и чем дальше он от второго, тем выше уверенность. Коэффициенты
подогнаны так, чтобы средняя уверенность совпадала с долей верных кодов (калибровка).

Зоны: от 85 процентов `high`, от 60 `medium`, ниже `low`. Автоматически (`auto`) код
принимается только в зоне `high`, если код действующий и строка похожа на товар. Остальные
позиции получают `needs_review`. Функция `explain` собирает пояснение «почему этот код» из общих
слов, совпавших характеристик и числовых границ, это обычный текст без нейросети.

### chooser.py

Второе мнение по спорным позициям. В нейросеть уходят только позиции `needs_review` с больше чем
одним кандидатом, по пять в запросе. Чтобы не раздувать запрос, кандидатам оставляют только те
характеристики, значения которых различаются (`differing`). Ответ принимается, только если код
есть среди кандидатов этой позиции. Бюджет времени `LLM_CHOOSE_BUDGET` (90 секунд), и никогда не
позже `JOB_TIME_LIMIT`. Выключается переменной `LLM_CHOOSE=0`.

## 7. База данных

Схема создаётся при старте командой `create_all`, миграций нет. Поэтому новое поле в модель
нужно добавлять осторожно: к уже существующей базе колонка сама не добавится.

Таблица `jobs`:

| Поле | Что это |
| --- | --- |
| `id` | uuid, он же имя файла на диске |
| `filename` | имя загруженного файла |
| `status` | `queued`, `processing`, `done`, `failed`, `cancelled` |
| `total`, `processed` | сколько строк в файле и сколько готово |
| `error` | текст ошибки для пользователя |
| `include_inactive` | учитывать ли недействующие коды |
| `created_at`, `started_at`, `finished_at` | время |
| `stage_seconds` | JSON: секунды по этапам `read`, `extract`, `search`, `confidence`, `choose`, `total` |

Таблица `items`:

| Поле | Что это |
| --- | --- |
| `id`, `job_id`, `row_number` | позиция, задание (внешний ключ с каскадным удалением), номер строки файла |
| `raw_text` | текст строки, ушедший в нейросеть |
| `attributes` | JSON: `name`, `brand`, `model`, `characteristics`, `search_text`, `measure`, `source` (`llm`, `rules` или `manual`), `provider`, `fallback`, `columns` (исходные колонки), `original` (снимок для отката) |
| `candidates` | JSON: пять кандидатов, каждый со своими характеристиками |
| `ktru_code`, `ktru_name` | выбранный код и его название |
| `confidence`, `zone` | уверенность и зона |
| `status` | `auto`, `needs_review`, `corrected`, `accepted`, `failed` |
| `summary` | пояснение «почему этот код» |

Как меняется статус позиции:

```
обработка           -> auto или needs_review      (confidence.assess)
accept              -> accepted
ручной код (PATCH)  -> corrected
правка атрибутов    -> auto или needs_review      (код подобран заново)
revert              -> то, что было до accept или PATCH
ошибка на строке    -> failed
```

Индексы стоят на `items.job_id`, `items.status` и `jobs.status`. Строки заданий и позиций сами
по себе не чистятся: удалить задание можно кнопкой на сайте. По замеру 23 октября 33 тысячи
позиций занимали в базе около 95 МБ.

## 8. API

Адрес `/api`. Подробная документация со схемами запросов открывается на
http://localhost:8000/api/docs (только с этого компьютера).

| Метод и адрес | Что делает |
| --- | --- |
| `POST /api/jobs` | загрузить файл (поля `file`, `include_inactive`), ответ 202 и `job_id` |
| `GET /api/jobs?limit=` | задания от новых к старым, до 1000, в каждом `counts`; заголовок `X-Total-Count` с общим числом |
| `GET /api/jobs/{id}` | задание со `counts` и `fallback` |
| `DELETE /api/jobs/{id}` | удалить задание, позиции и файл; 409, если оно в работе |
| `GET /api/jobs/{id}/items` | позиции: `status` через запятую, `q`, `limit` до 200, `offset`, `candidates=false` |
| `GET /api/items/{id}` | одна позиция и её место в задании |
| `PATCH /api/items/{id}` | ручной код `{ktru_code}`, статус `corrected` |
| `PUT /api/items/{id}/attributes` | исправленные атрибуты, код подбирается заново |
| `POST /api/items/{id}/accept` | принять код |
| `POST /api/items/{id}/revert` | вернуть то, что предложила система |
| `POST /api/jobs/{id}/accept?min_confidence=` | принять все действующие коды с уверенностью не ниже порога |
| `POST /api/jobs/{id}/cancel` | остановить задание |
| `GET /api/jobs/{id}/export?format=xlsx\|csv` | выгрузка готового или остановленного задания |
| `GET /api/catalog/search?q=` | поиск кода по началу или словам, для ручной правки |
| `GET /api/health` | состояние каталога (`loading`, `ready`, `error`), число кодов, состояние нейросетей, провайдеры без ключей |

Ошибки приходят как `{"detail": "текст по-русски"}`, статус 400, 404, 409, 413, 422 или 503.
Каталог ещё не загружен: 503 на тех запросах, которым он нужен.

### Как устроено состояние

Глобального хранилища нет. Каждый экран сам запрашивает данные и держит их в `useState`.

- `JobScreen` опрашивает `GET /api/jobs/<id>` раз в секунду, пока задание в очереди или идёт.
  В ответе есть `counts`, по ним `Results` рисует число позиций в каждом статусе.
- `Results` перезапрашивает список, когда меняется `job.processed`, фильтры, поиск, страница или
  счётчик `version` (его увеличивают после массового принятия). Поэтому новые карточки
  появляются сами. Поиск откладывается на 300 мс, чтобы не слать запрос на каждую букву.
- `ItemScreen` держит позицию вместе с соседями (`prev_id`, `next_id`, `next_unreviewed_id`).
  После каждого изменения позиция запрашивается заново.
- Уведомления с кнопкой «Отменить» после «Принять» живут на уровне всего приложения
  (`App` из antd в `App.tsx`), поэтому не пропадают, когда страница переходит к следующей
  позиции.

### Ошибки загрузки

`JobScreen` различает три случая (`loadProblem`): задания нет (404, повторять нечего), ошибка
сервера, нет связи. В двух последних есть кнопка «Повторить»: она убирает ошибку (на экране
появляется заготовка) и делает запрос заново. `ApiError` хранит код ответа в `status`.

### Стили

Всё оформление в `theme.css`, в компонентах цветов нет. Значения совпадают с макетом в Figma («v2 · Стили»). Файл начинается с переменных `:root`:
цвета (`--ink`, `--accent`, `--primary-bg`, `--green`, `--amber`, `--red` и производные),
размеры (`--text`, `--s1`...`--s8`), скругления. Затем идут блоки по частям интерфейса:
шапка, кнопки, загрузка, плитки, окно прогресса, карточки списка, параметры, страница позиции,
адаптив для узких экранов. Стиль: светлая страница, белые карточки с крупными скруглениями и
мягкими тенями, один синий цвет, шрифт Inter. Тема одна, светлая. Цвета статусов и зон уверенности
всегда сопровождаются словом: у статуса цветная точка и название, у уверенности число.

Настройки antd (`readTokens` в `App.tsx`) читаются из тех же переменных `theme.css`, чтобы поля
ввода и меню выглядели как остальной сайт.

### Тексты

Все надписи лежат в `texts.ts`, объект `T`. Тексты с подстановкой это функции, например
`T.results.pageShown(from, to, total)`. Чтобы поменять надпись, правьте только этот файл.

## 10. Нейросети и ключи

Порядок и список задаёт `LLM_PROVIDERS`. Сейчас это пять ключей Gemini (`gemini` и
`gemini2`...`gemini5`, по одному на аккаунт Google, у каждого свой проект и свои лимиты) и
GigaChat. Gemini идут первыми, GigaChat запасной: к нему пачка уходит, только когда ни один
Gemini не может её взять (ошибка, нет ключа, пауза после сбоя).

Лимиты бесплатного Gemini 3.5 Flash Lite: 15 запросов в минуту и 500 в день на ключ. Поэтому
у каждого ключа стоит `GEMINI_RPM=14`, запросы растягиваются во времени, и 429 приходит редко.
У GigaChat на бесплатном тарифе один поток (`GIGACHAT_PARALLEL=1`): на второй одновременный
запрос он отвечает 429.

Как добавить ещё один ключ Gemini: впишите в `.env` строку `GEMINI6_API_KEY=...` и добавьте
`gemini6` в `LLM_PROVIDERS`, потом `docker compose up -d backend`. Остальные значения возьмутся
из `GEMINI_*`. Проверка: `docker compose exec backend python check_llm.py`.

Как добавить другой OpenAI-совместимый сервис: в `LLM_PROVIDERS` имя, например `myapi`, и
строки `MYAPI_BASE_URL`, `MYAPI_API_KEY`, `MYAPI_MODEL`, `MYAPI_PARALLEL`, `MYAPI_RPM`. Менять
код не нужно.

Если ключей нет совсем, сайт работает, но атрибуты извлекаются правилами и точность ниже.
На странице такой позиции, во вкладке «Строка и атрибуты», написано, почему не сработала нейросеть.

## 11. Скорость и узкие места

Требование организаторов: 1000 позиций не дольше 5 минут. Замеры 23 октября 2026 на файле
организаторов «Спецификация_1000_без_КТРУ» при пяти ключах Gemini и видеокарте:

Время от загрузки до готовности в четырёх прогонах: 115, 117, 159 и 160 секунд. По записанным
этапам (`stage_seconds` задания) два из них выглядят так:

| Этап | Прогон 1 | Прогон 2 |
| --- | --- | --- |
| извлечение атрибутов (ожидание ответов нейросетей) | 79 с | 98 с |
| поиск вместе с эмбеддингами | 27 с | 30 с |
| второе мнение по спорным | 30 с | 30 с |
| всего | 138 с | 158 с |

Разброс идёт от скорости Gemini: запрос с пачкой строк отвечает от нескольких секунд до 20. Строк, обработанных правилами, во всех прогонах 0. Жёсткий потолок времени
`JOB_TIME_LIMIT` 270 секунд гарантирует, что задание закончится вовремя, даже если сети тормозят:
после бюджета извлечения (`LLM_BUDGET` 240 с) оставшиеся строки получают атрибуты от правил,
а второе мнение никогда не идёт дольше потолка.

Где тратится время и что уже сделано:

- Извлечение атрибутов (основная часть, 80-100 с). Определяется скоростью нейросетей. Что
  сделано: пять ключей Gemini работают параллельно (по четыре запроса на ключ), по 20 строк в
  запросе, пока одна пачка ждёт ответа, следующие уже отправлены, быстрые ключи сами берут
  больше пачек, ответ, обрезанный по длине, делится пополам, а не уходит к другому провайдеру.
- Эмбеддинги. На видеокарте тысяча строк считается около 20 секунд, на процессоре около четырёх
  минут, поэтому GPU подключается из `.env`. Одинаковые тексты не пересчитываются.
- Поиск. Точный косинус по матрице считается пачками по 128 запросов. В сумме поиск и
  эмбеддинги занимают 25-30 секунд на тысячу строк и идут параллельно с запросами к нейросетям.
- Второе мнение (около 30 секунд). Выполняется после всех строк, и только для спорных.
- Передача данных. nginx сжимает ответы gzip: скрипт сайта 838 КБ передаётся как 264 КБ.
  Список карточек не отдаёт пять кандидатов (`candidates=false`): ответ на 20 карточек уменьшился
  с 210 КБ до 53 КБ (с gzip около 9 КБ). Список заданий отдаёт готовность каждого задания
  одним запросом, а не сотней. Выгрузка не читает кандидатов из базы.
- Интерфейс получает готовые строки по мере обработки, пользователь работает с ними, не ожидая
  конца.

## 12. Безопасность

- Загрузка. Размер не больше 10 МБ, начало файла должно совпадать с расширением, xlsx и docx
  проверяются на zip-бомбу, число ячеек и страниц ограничено. Файл хранится под uuid.
- Нейросети. Текст строки отправляется как данные, ответ проходит проверку «значение есть в
  исходной строке». Код, выбранный нейросетью, должен быть среди кандидатов.
- Выгрузка. Ячейки, начинающиеся с `=`, `+`, `-`, `@` (в том числе после пробелов или переноса
  строки), получают апостроф: формула в Excel не выполнится.
- nginx. Заголовки `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
  `Permissions-Policy` и `Content-Security-Policy`. Загрузки ограничены 20 в минуту с одного
  адреса. Документация API закрыта для сети, backend открыт наружу только на 127.0.0.1.
- Контейнеры. Backend, nginx и Ollama работают без прав root.
- Секреты. Ключи только в `.env` (он в `.gitignore`). `/api/health` отдаёт имена провайдеров и
  лимиты, ключи никогда.
- Известная слабость: проверка сертификата GigaChat выключена по умолчанию (в примере Сбера
  так же). Для боевого запуска укажите путь к корневому сертификату в `GIGACHAT_VERIFY_SSL`.

## 16. Типовые правки

Поменять порог автоматического принятия. `HIGH` и `MEDIUM` в `backend/confidence.py`. После
смены прогоните `scripts/evaluate.py` и посмотрите точность зоны `high`.

Поменять формулу уверенности. Коэффициенты `W_SCORE`, `W_MARGIN`, `BIAS` в том же файле.
Их подбирали по замеру, так что меняйте только вместе с новым замером.

Изменить правила ранжирования кодов. Константы в начале `backend/search.py`. Правило такое:
любая правка, которая меняет точность, проверяется до и после на двух наборах сразу (файл
организаторов на 1000 строк и реальная спецификация на 12 строк). Улучшение на одном при
ухудшении на другом не принимается.

Поменять промпт нейросети. `SYSTEM_PROMPT` в `backend/extractor.py` (атрибуты) или в
`backend/chooser.py` (второе мнение). Проверка так же: замер до и после.

Добавить колонку в выгрузку. `EXPORT_HEADER` и `export_rows` в `backend/api.py`. Колонки
исходного файла добавляются автоматически.

Добавить статус позиции. Допишите его в `ITEM_STATUSES` и `STATUS_TEXT` в `api.py`, в
`ItemStatus` в `frontend/src/api.ts`, в `T.itemStatus` в `texts.ts`, в `STATUS_ICONS`,
`STATUS_TONE` и `MARK_ICONS` в `ui.tsx`.

Поменять текст на сайте. Только `frontend/src/texts.ts`.

Поменять цвет или размер. Переменная в `:root` в начале `frontend/src/theme.css`.

Добавить страницу. Адрес и разбор в `router.ts` (`parseRoute`, тип `Route`, `paths`), экран в
новом файле, выбор экрана в функции `page()` в `App.tsx`, пункт меню в шапке, если нужен.

Изменить число строк в файле. `MAX_ITEMS` в `backend/parser.py` и текст в `texts.ts`
(`upload.dropHint`). Учтите, что время обработки растёт почти линейно.

Добавить поле в базу. Измените модель в `api.py`. Миграций нет, поэтому для работающей базы
понадобится либо ручной `ALTER TABLE`, либо новая база (`docker compose down -v`).

Новый ключ или провайдер. Раздел 10.

## 18. Ограничения и что можно улучшить

Ограничения, о которых стоит знать.

- Не больше 1000 позиций и 10 МБ на файл.
- Каталог целиком в памяти backend (около 334 МБ плюс рабочая память), масштабировать backend
  горизонтально неудобно: у каждой копии свой каталог.
- Миграций базы нет, схема создаётся `create_all`.
- Нет авторизации и разделения пользователей: все задания видны всем, кто открыл сайт.
- Задания и позиции не удаляются сами, только вручную.
- Скорость зависит от внешних нейросетей: бесплатные тарифы Gemini ограничены 500 запросами в
  день на ключ, GigaChat на бесплатном тарифе отвечает одному потоку.
- Список заданий показывает до 1000 заданий.

Что можно улучшить, если останется время.

- Запускать второе мнение сразу для готовых пачек, не дожидаясь конца файла. Сейчас оно
  идёт после всех строк и занимает около 30 секунд из 120-160.
- Разнести `api.py` (834 строки) на модели, очередь, выгрузку и маршруты. Файл уже больше
  рекомендованных 300 строк, как и `search.py`.
- Добавить миграции (Alembic).
- Очистка старых заданий по сроку.
- Номера страниц в списке заданий вместо кнопки «Показать ещё».

| № | Критерий | Метрика | Результат |
