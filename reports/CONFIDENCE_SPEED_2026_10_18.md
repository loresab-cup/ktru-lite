# Уверенность, повторные файлы и совместная проверка

Продолжение отчёта REVIEW_2026_10_18.md. Изменения находятся только в локальной ветке
`codex/review-processing-20261018`; push и изменение main не выполнялись.
Пользователь разрешил использовать имеющиеся данные, независимого размеченного эталона нет.

## Что принято

- При равенстве оценок первых кандидатов полный код больше не назначается автоматически.
  Формула процентов и пороги зон не изменены; пояснение прямо сообщает о неоднозначности.
- Ручной выбор больше не подменяет оценку числом 100%. Показывается «Исправлено», а числовая
  оценка нового кода отсутствует. Это не откалиброванная вероятность человеческого решения.
- Ответы LLM, прошедшие существующую проверку значений по исходной строке, переиспользуются
  для точно равных исходных текстов. Кеш в памяти: 5000 записей, 30 минут, отдельный контекст
  провайдера, модели, промпта, адреса и подключения. Ошибки и ответы правил не сохраняются.
  Данные возвращаются копиями; изменение характеристик в интерфейсе кеш не меняет.
  После перезапуска сервера кеш пуст. Между экземплярами backend он не разделяется.
  Поиск и проверка кодов выполняются заново по текущему каталогу.
- В карточке появилась совместная проверка похожих строк одного задания. Для предложения
  группы совпадают исходное наименование, извлечённые название/бренд/модель/характеристики,
  единица и набор кандидатов. Группа не доказывает равенство исходных требований: все исходные
  тексты доступны перед выбором, пользователь явно подтверждает применимость общего кода.
  Ручные исправления, принятые и автоматические строки не заменяются. Новые строки, правки или
  изменение группы после просмотра приводят к 409, а не к применению устаревшего решения.
  Для PostgreSQL записи блокируются на время сохранения; индивидуальные правки тоже используют
  блокировку. В тестовой SQLite проверены конфликт устаревшего снимка и границы задания.
- Исправлены повторяющиеся React-ключи редактора и поиска в карточке.

## Скорость: реальные запросы на синтетическом файле

Среда прежняя: Ryzen 5 7535HS, 16 ГБ RAM, Docker около 7.36 GiB, BGE-M3 на CPU,
Yandex qwen3.6-35b-a3b, 4 запроса одновременно, один обрабатываемый файл,
изолированная SQLite и тот же каталог из 81 509 кодов. Тяжёлые задания не пересекались.
Короткие проверки кода и интерфейса выполнялись отдельно от иных нагрузочных заданий.

| Полный путь от загрузки до готовности | Предыдущая итерация | Эта итерация |
|---|---:|---:|
| Холодный запуск 1000 строк | 125.17 с | 145.57 с |
| Повтор того же файла | 79.54 с | 20.64 с |
| Строки с повторно использованным ответом LLM | 0 | 1000 при повторе |

Ускорение подтверждено для повторного файла, на 74%. Ускорение холодного запуска не получено;
он остался в пределах 200 секунд. Для новых строк по-прежнему нужны обращения к модели.
Холодный запуск: сервер перезапущен, кеши приложения пусты, BGE выгружена из Ollama;
готовности каталога дождались до загрузки. Повтор выполнен без перезапуска и очистки кешей.
1000/1000 строк распознаны LLM, ни одного ответа правил. В холодном запуске 100 HTTP 200
от Yandex, в повторном — 0 новых запросов к LLM. Все 1000 выбранных кодов, статусов и оценок
холодного/повторного запуска совпали. CSV и XLSX доступны в обоих случаях.

Этапы холодного запуска: чтение 1.33 с, ожидание извлечения 8.50 с, эмбеддинги 114.31 с,
поиск 12.76 с, сохранение 5.78 с, серверная обработка 142.87 с. Повтор: чтение 0.14 с,
извлечение/эмбеддинги менее 0.01 с, поиск 11.10 с, сохранение 5.28 с, сервер 16.74 с.
Разница до полного времени включает очередь, HTTP и период опроса клиента.

## Качество и ручная работа

Это синтетическое самовосстановление каталога: 1000 тех же строк и исходных векторов каталога,
а не независимая проверка реальных закупок. Одинаковые названия и характеристики нескольких
полных кодов делают часть примеров неоднозначной. Поиск не менялся, хеш всех назначений совпал.

| Показатель | До защиты равных кандидатов | После |
|---|---:|---:|
| Точный полный код в первом кандидате | 855/1000 (85.5%) | 855/1000 (85.5%) |
| Правильный полный код в топ-5 | 958/1000 (95.8%) | 958/1000 (95.8%) |
| Автоматические назначения | 790 | 746 |
| Ошибочные автоматические назначения | 119 | 92 |
| Ошибочные среди автоматических | 15.06% | 12.33% |
| Строки для ручного подтверждения | 210 | 254 |

Это улучшение осторожности автоматики, но оставшийся уровень ошибок не позволяет считать
проценты откалиброванной вероятностью правильности полного кода. Снижение порога ради числа
автоматических ответов не выполнялось.

У файла spec_1000.xlsx нет проверенных полных кодов: точность/top-5/ошибки автоматики для него
неизвестны. В новом холодном запуске 40 строк auto и 960 needs_review. Эти 960 строк дают
574 группы (134 группы содержат несколько строк, максимум 21). Потенциально это на 40.2%
меньше отдельных решений по выбору кода, если просмотр исходных текстов подтверждает общий
выбор. Это не измерение сокращения времени чтения и не разрешение принимать все группы вслепую.

## Отклонённый эксперимент

Замена полного запроса на короткий search_text ускорила эмбеддинги+поиск на фиксированных
LLM-атрибутах 1000 строк: 107.31 → 44.62 с; уникальных запросов 995 → 563.
Но на отдельном синтетическом наборе 200 кодов с фиксированными характеристиками:

| Показатель | Полный запрос | Короткий запрос |
|---|---:|---:|
| Точный первый код | 154 | 156 |
| Топ-5 | 198 | 197 |
| Ошибочные auto по прежней формуле | 25 | 30 |

Из-за ухудшения топ-5 и автоматических назначений короткий запрос **не включён** в обработку.
В репозитории оставлен только воспроизводимый диагностический скрипт benchmark_semantic.py.
Повторный разбор сохранённых кандидатов с новой защитой: для полного запроса auto 159,
ошибочных auto 21; поиск и топ-5 от защиты не меняются. Независимой точностью это не является.

## Проверка и артефакты

- Backend: 123 теста, без пропусков; Ruff check/format. Frontend: lint, production build,
  тест транспорта API — зелёные.
- Тесты покрывают TTL, ограничение памяти, смену модели, изменение источника, изоляцию копий,
  отсутствие кеширования fallback, отмену задания с кешем, устаревший групповой снимок,
  сохранение ручных решений и границы задания/характеристик.
- В браузере: исходные 4 строки группы клавиатур раскрыты, до подтверждения кнопка заблокирована;
  после подтверждения все 4 получили «Исправлено», группа исчезла, числовая оценка не выдумана.
  Это проверка механики интерфейса на синтетическом задании, не разметка эталона.
- JSON: review-20261018-confidence-cold.json, confidence-warm.json, confidence-summary.json,
  confidence-retrieval.json; скриншоты group-preview.jpg и group-saved.jpg.
- Исходные построчные данные больших замеров остаются в локальной игнорируемой .benchmark.

Предпросмотр: http://127.0.0.1:5188/. Рабочие контейнеры на порту 3000 не пересобирались,
производственная база не менялась. Новые функции доступны в тестовом предпросмотре и исходниках
отдельной ветки. Для презентации скорость подтверждена; точность на реальных закупках ещё
нуждается в независимом эталоне и калибровке.
