## 4. Проверка интеграции GigaChat

- Отправка спецификации → очередь → пакетное извлечение → поиск → результаты → CSV:
  проверено через настоящий FastAPI TestClient и реальный каталог. Сетевой провайдер имитируется.
- Исправление кода/атрибутов, принятие, фильтрация, CSV и XLSX: существующий интеграционный тест проходит.
- Кэш OAuth, 401 и обновление токена, ограничения параллельности, тайм-ауты,
  недоступность сети, причины fallback: существующие и новые тесты проходят.
- 429 и 500/503 с успешным повтором: проверены; в тесте убрано только ожидание между повторами.
- Пустой/слишком большой файл, неправильное расширение/сигнатура, 1001 строка,
  пробельное/длинное имя, некорректные поля ответа модели: проверены.
- TXT UTF-16, CSV, XLSX, DOCX проверяются самостоятельно созданными файлами;
  PDF проверен на пустой документ и внешние текстовые fixtures. При итоговом запуске найдены все 9 внешних fixtures соседнего проекта `b2b`; они тоже проходят.
- Набор из 1000 записей проверяется на точное совпадение с результатом parser и повторяемость генерации.
- Ожидание медленной загрузки не блокирует health: проверено конкурирующими запросами.
- API-клиент frontend проверен на успешный JSON, HTTP-ошибку, HTML от прокси,
  испорченный JSON, сетевой сбой и отмену по тайм-ауту. Визуальный сценарий в браузере не проходился.
- Истории диалогов нет; контекст — system prompt и текущий пакет строк.
  Проверка значений ответа по исходной строке сохранена.

Живой GigaChat не вызывался. Ключ настроен, но нет разрешения на платную нагрузку
и данных о тарифе/остатке квоты. При 1000 уникальных строк требуется 100 первичных
chat-вызовов; с двумя повторами — до 300 попыток, с лимитом 4096 выходных токенов
на попытку. Цена в рублях без тарифа и фактического токенизатора не утверждается.
Нельзя считать, что ответ и точность реальной модели проверены имитатором.

## 5. Нагрузочные проверки

Windows, Python 3.12, SQLite во временной папке; PostgreSQL не имитируется.
Использован реальный неизменённый дамп, 81 509 кодов.
Ollama заменена существующим режимом словесного поиска; GigaChat — HTTPX MockTransport
с искусственным ожиданием 5 мс, тем же форматом OAuth/chat и той же моделью в запросе.
Глобальный семафор ограничивает транспорт одним запросом.
Рабочие файлы, БД и загрузки пользователя не использовались.

Каждый прогон включает A/B/C для извлечения и отдельно A/B/C через HTTP API.
Конкурентность повышается 1 → 2 → 4 → 8. Полное время задания включает ожидание
воркера, опрос раз в 50 мс, обработку и CSV-выгрузку. Это не чистое время модели.
Поле requests для API означает число заданий, а для extraction — число пакетов.
Все числа успешных/неуспешных запросов, тайм-ауты, CPU, память и задержки

Backend ruff check/format проходят; frontend transport test, oxlint и production build проходят.
Backend проверен импортом, тестами и compileall непосредственно в репозитории; Docker-образ не собирался. Frontend собран и проверен в изолированной копии с теми же файлами приложения и package-lock; зависимости установлены через npm ci.
Модель, ранжирование и API сохранены. На одном прогоне измерения немного колеблются;
оснований объявлять статистически значимое ускорение нет.
Практический выигрыш — устранение подтверждённых отказов и блокировки event loop,
отказ от загрузки всех JSON-атрибутов в Python при каждом запросе прогресса.

## 7. Оставшиеся риски и ограничения

Docker Desktop daemon недоступен: полный compose, nginx и PostgreSQL под нагрузкой не проверены.
Не запускались платная нагрузка, реальная генерация GigaChat, реальная Ollama,
браузерная приёмка и проверка точности на размеченном эталоне.
Результаты SQLite/словесного поиска нельзя переносить на PostgreSQL/эмбеддинги/живую модель.
Набор синтетический, оценки точности кодов КТРУ по нему не делались.
Повторы замеров не являются контролируемым статистическим экспериментом.
Starlette показывает deprecation warning об использовании httpx в TestClient;
зависимости production ради подавления предупреждения не менялись.
Нерешённые проблемы и условия их проявления перечислены в разделе 3.

## 8. Рекомендации

1. Включить проверку TLS с доверенным CA; ограничить доступ к API до публикации сервиса.
2. Проверить один небольшой реальный запрос после согласования тарифа/стоимости;
   отдельно измерить реальные модельные задержки и расход токенов, затем плавно увеличить объём.
3. Запустить Docker/PostgreSQL/Ollama и браузерную приёмку загрузки, правки и обеих выгрузок.
4. Проверить восстановление после отказа БД и остановки процесса, затем решать lease заданий
   и корректное завершение фоновых потоков, не меняя API без необходимости.
5. Добавить воспроизводимый размеченный эталон для качества подбора КТРУ и CI для текущих проверок.
