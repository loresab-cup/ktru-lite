# Задание команде и AI-агенту: тестирование ЕИС Классификатора

Передайте этот файл своему AI-агенту и попросите выполнить его полностью.

## Цель

Получить актуальную версию проекта из GitHub, запустить её, проверить приложение
и составить отчёты. Вы работаете как тестировщик. Исправления выполняет разработчик
после разбора ваших находок.

Репозиторий: https://github.com/loresab-cup/ktru-lite
Ветка для проверки по умолчанию: `main`. Если координатор дал другую ветку,
используйте именно её. Не объединяйте несколько веток самостоятельно.

## Обязательные ограничения

1. **Не изменять код приложения, тесты, зависимости и настройки сборки.** Нельзя
   исправлять импорты, переименовывать файлы, менять промпт, веса поиска, пороги
   уверенности, миграции, Dockerfile, Compose, lock-файлы и эталонные ответы.
2. Если найден баг, воспроизведите его и запишите в `bags.md`. Не исправляйте даже
   очевидную опечатку в коде. Не включайте автоматические исправления линтера/форматтера.
3. Предложения по структуре, удобству, скорости и качеству записывайте в `improve.md`.
   Подозрение без воспроизведения тоже допустимо, но помечайте его как гипотезу.
4. Разрешены отчёты `bags.md`, `improve.md`, `test-report.md`, а также временные
   тестовые входные файлы, скрипты и доказательства внутри `outputs/team-testing/`.
   Временные скрипты не должны менять исходники или эталоны.
5. Разрешено заполнить локальный `.env` по инструкции запуска. Не отправляйте
   ключи, пароли, cookie и содержимое `.env` в отчёты, скриншоты или Git.
6. Используйте отдельные тестовые аккаунты и синтетические/согласованные файлы.
   Не трогайте аккаунты, пароли, спецификации и базы других людей.
7. Не выполняйте `git reset --hard`, `git clean -fd`, принудительный checkout,
   принудительный push, удаление рабочих Docker-томов и `docker compose down -v`.
8. Не начинайте реализацию исправлений после завершения тестирования. Итог этой
   задачи — отчёты и доказательства. Коммитить или отправлять отчёты в Git можно
   только по отдельному поручению координатора.

## 1. Получить последнюю версию

Предпочтительно сделать отдельную чистую копию для тестирования:

```sh
git clone https://github.com/loresab-cup/ktru-lite.git ktru-lite-testing
cd ktru-lite-testing
git switch main
git pull --ff-only origin main
git rev-parse HEAD
git status --short
```

Если папка уже существует, сначала прочитайте `git status --short`, текущую ветку
и remote. Обновляйте её только при чистом рабочем дереве и нужной ветке.
При локальных изменениях или расходящейся истории используйте отдельный clone;
не удаляйте и не прячьте чужую работу автоматически.

Запишите полный SHA коммита, дату, имя тестировщика, ОС, RAM и версию Docker.
Этот SHA фиксирует проверяемую версию. Во время прогона больше не делайте pull.
Если разработчик прислал исправление, проверяйте его отдельно с новым SHA.

Читайте актуальные `README.md`, `README_FULL.md` и инструкции репозитория.
Названия модулей могли поменяться: не восстанавливайте старые файлы и импорты
ради запуска. Ошибка актуальной инструкции — отдельный баг.

## 2. Подготовить окружение

- Скопируйте `.env.example` в `.env` и заполните выданные координатором настройки.
- Для пяти аккаунтов Яндекса нужны пять корректных пар API_KEY/FOLDER_ID.
  Папки и облака различаются; пять ключей не гарантируют пять независимых квот.
- Сайт может использовать один ключ, но сравнивать его скорость с замером пяти
  ключей без указания различий нельзя. В отчёте приводите число ключей,
  параллельность, размер пакета и названия моделей, без секретных значений.
- Запускайте по текущему README. Обычная команда: `docker compose up --build`.
- Сайт: http://localhost:3000. Состояние: http://localhost:8000/api/health.
  Дождитесь готовности каталога и worker, зафиксируйте количество кодов.
- Каталог большой, первый запуск скачивает данные и занимает время. Первую
  подготовку каталога не включайте во время классификации загруженного файла.
- Если порты/контейнеры заняты другой установкой, не останавливайте её. Согласуйте
  отдельную машину или окружение. Имя проекта Compose в файле фиксировано,
  поэтому отдельная папка сама по себе не изолирует Docker-тома и порты.

Вызовы нейросетей расходуют деньги. Координатор согласует бюджет и порядок
массовых прогонов. До этого выполняйте локальные проверки без внешних запросов.
Не запускайте все датасеты многократно и одновременно со всей командой.
Общие облачные ключи делят квоты даже на разных компьютерах.

## 3. Проверки без платных запросов

В отдельном тестовом окружении с зависимостями из `requirements-dev.txt`:

```sh
cd backend
python -m pytest -q tests
ruff check --line-length 100 .
ruff format --check --line-length 100 .
```

Из `frontend/`:

```sh
npm ci
npm test
npm run lint
npm run build
```

Не устанавливайте зависимости в чужое рабочее окружение. Не используйте
`ruff --fix`, форматирование без `--check`, `npm audit fix` или обновление пакетов.
Пропущенные тесты перечисляйте отдельно с причинами. Отсутствующая тестовая
PostgreSQL или fixtures не означают, что соответствующий функционал проверен.

## 4. Пользовательские сценарии

Для каждого шага фиксируйте: успешно / ошибка / не проверено и доказательство.

### Вход, гостевой режим и личные данные

- Первый визит, политика и необходимые согласия; документы читаются до входа.
- Проверить актуальный сценарий гостя, регистрации, входа и выхода.
- После входа ожидается главная страница, состояние шапки соответствует пользователю.
- Новый аккаунт не видит чужих недавних спецификаций.
- Создать аккаунты A и B. Загрузить файл в A; в B проверить список и прямые URL
  задания, строки, выгрузки, изменения и удаления. Ожидать отказ без чужих данных.
- Если гостевые файлы переносятся после входа, проверить перенос только своему
  аккаунту и отсутствие доступа у другого гостя/пользователя.
- Смена логина и пароля, неверный текущий пароль, занятый логин, повторный вход.
  Менять пароли только собственных временных аккаунтов.
- Проверить добровольность улучшения сервиса и поведение отзыва согласий по
  актуальному интерфейсу. Не проставлять согласия от имени реальных пользователей.

### Загрузка и обработка

- Небольшие XLSX, CSV, текстовые PDF; дополнительно заявленные DOCX и TXT.
- CSV с разными разделителями, русским текстом, кавычками и переносами строк.
- Таблицы с несколькими листами, пустыми строками, служебными итогами и формами ЕИС.
- Отдельно: пустой файл, неверное расширение/содержимое, повреждённый документ,
  превышение заявленных лимитов. Ожидать понятную ошибку и работоспособность сайта.
- Пустые название/бренд/модель и отсутствующие характеристики не должны
  превращаться в выдуманные сведения. Для аксессуаров проверить, не присвоен
  ли бренд совместимого оборудования самому аксессуару.
- Обновление страницы во время обработки, уход на другую страницу, возврат,
  отмена задания, повторная загрузка, удаление собственного завершённого задания.
- Прогресс обновляется, готовые строки доступны, браузер не блокируется.

### Результаты и экспорт

- Поиск, сортировка, фильтры, страницы результатов и массовый выбор.
- Коды, названия, характеристики, единицы измерения, причины сомнений и уверенность.
- Процент не считать доказанной вероятностью правильности. Ручное решение
  отличать от автоматического предложения; не требовать выдуманного 100%.
- Заменить код на ДРУГОЙ допустимый код, сохранить, обновить страницу и проверить.
- Проверить принятие, отмену правки и групповое применение к одинаковым строкам.
- Скачать CSV и XLSX, открыть/прочитать: количество строк, исправленный код,
  русские символы, характеристики, отсутствие потерь и перепутанных столбцов.
- Проверить текст, похожий на формулу (`=1+1`), на собственном тестовом файле:
  в экспортируемой текстовой ячейке он не должен становиться активной формулой.
- Узкий экран, длинные названия, управление клавиатурой, сообщения об ошибках.

## 5. Качество и нагрузка — по согласованному бюджету

1. Распознавание атрибутов: отдельная разметка, оценка имени/бренда/модели по
   каждому полю, отдельно заполненные и отсутствующие значения. Не меняйте эталон
   после просмотра ответов. Спорную разметку укажите отдельно и объясните.
2. 1000 позиций: вход без КТРУ, сравнение с отдельным эталоном. Цели кейса:
   >=85% точных кодов и <300 секунд. Засекать от начала отправки файла до `done`;
   время API-ответа 202 и ожидание очереди приводить отдельно.
3. Отмечать число fallback, words_only, failed, пропущенных строк и процентов.
   Успешный статус задания сам по себе не доказывает хорошее качество.
4. PDF >50 страниц: записать происхождение, число страниц, текстовый слой,
   ожидаемое/фактическое количество товаров. Проверить через порт 3000 без 504.
   PDF, экспортированный из Word, обозначать именно так; не называть независимым
   реальным документом. Повторённые страницы не считать таким доказательством.
5. Несколько одновременных загрузок: сначала 2, затем до 5 пользователей в
   согласованном окружении. Измерить ожидание очереди, время завершения, CPU/RAM,
   ошибки и 429. Не устраивать бесконтрольный стресс-тест публичного сайта/API.
6. Проверки отказа worker/Redis выполнять только в отдельной установке после
   согласования. Не останавливать рабочую базу команды. Проверить, что задания
   восстанавливаются без дублей и потери ручных правок.

Один тестировщик делает большой замер, остальные проверяют функциональные
сценарии. Повторять дорогой прогон только для конкретной гипотезы или исправления.

## 6. Файлы отчётов

Создайте в корне своей тестовой копии `bags.md`, `improve.md`, `test-report.md`.
Если они уже существуют, сохраняйте содержимое и дополняйте: не затирайте историю.
Перед добавлением найдите дубликаты. Используйте префикс тестировщика в ID,
например `AK-BUG-001`, чтобы отчёты команды не конфликтовали по номерам.

### bags.md — воспроизводимые ошибки

```md
### AK-BUG-001 — Короткое название
Статус: открыто / воспроизводится не всегда / не воспроизведено повторно
Приоритет: P0 / P1 / P2 / P3
Версия: полный SHA; дата; ОС; браузер
Условия: пользователь/гость, формат, параметры без секретов
Шаги: точная последовательность действий
Ожидалось: требование ТЗ, README или согласованного поведения
Получилось: наблюдаемый результат
Воспроизводимость: 3 из 3 попыток (или фактическое значение)
Доказательства: путь к входному файлу, скриншоту, безопасному логу
Последствия: кто и как страдает, возможен ли обход
Предполагаемое место: файл/функция/строка; гипотеза, если причина не доказана
```

P0 — потеря/раскрытие чужих данных или полная неработоспособность;
P1 — сломан основной сценарий; P2 — частный сценарий; P3 — мелкая ошибка интерфейса.
Не присваивайте P0 только из-за неудобного текста или медленной первой установки.
Если ошибок нет, напишите «В проверенных сценариях баги не обнаружены» и дайте
ссылку на покрытие. Не утверждайте, что во всём проекте ошибок нет.

### improve.md — предложения и гипотезы

```md
### AK-IMP-001 — Короткое название
Наблюдение: что неудобно или вызывает сомнение
Основание: сценарий/замер/ссылка на код
Предложение: что стоит обсудить разработчикам
Польза: ожидаемый результат для пользователя
Приоритет и риски: кратко
Статус доказательств: подтверждено измерением / гипотеза
```

Не требуйте переписать архитектуру без конкретной измеренной причины.
Косметическое улучшение не объявляйте нарушением ТЗ. Возможную уязвимость
опишите осторожно; не объявляйте эксплуатацию доказанной без безопасного воспроизведения.

### test-report.md — итог

- Тестировщик, дата, ветка, полный SHA, окружение и способ запуска.
- Какие проверки выполнены, их фактические результаты и доказательства.
- Сколько тестов passed/failed/skipped и почему были пропуски.
- Таблица сценариев: ID, проверка, результат, ссылка на баг/доказательство.
- Качество, время и нагрузка с условиями замера, без заимствования чужих цифр.
- Список непроверенного и блокировок: нет ключей/бюджета/документа/оборудования.
- Заключение: готово к демонстрации / нужно исправить перечисленные ошибки /
  данных для вывода недостаточно. Вывод должен следовать из ваших проверок.
- Итоговый `git status --short` и подтверждение, что код не менялся.

## 7. Передать результат

Удалите только свои временные аккаунты и данные, если это безопасно и обработка
уже завершена. При невозможности очистки укажите точные тестовые объекты координатору.
Не чистите чужую базу и общие Docker-тома.

Проверьте diff: допустимы только отчёты; конфигурация `.env` и временные доказательства
остаются локально. Если команда сборки изменила отслеживаемый файл, сообщите об этом,
не коммитьте его и не маскируйте изменение автоматическим откатом.

Отправьте координатору три отчёта и необходимые обезличенные доказательства.
В чат кратко: какой SHA проверен, что удалось проверить, главные баги, что блокирует
сдачу и что осталось непроверенным. На этом завершите работу без исправления кода.
