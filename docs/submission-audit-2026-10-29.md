демонстрировать. Полную готовность к передаче жюри пока нельзя подтвердить:

| 1000 позиций менее 5 минут | Замер 28.10: 192,612 секунды | Выполнено на прежнем проверенном состоянии и пяти ключах; финальный повтор нужен |
| Процент уверенности для каждого товара | Формула по сходству и отрыву кандидата; исправлена оценка после второго мнения. Свежий запрос: 9222 автоматических предложения с кодом, 0 отсутствующих/выходящих за диапазон оценок | Автоматические предложения покрыты; оговорка о ручных результатах ниже |
| Ручная корректировка | Диалог выбора кода, PATCH, принятие/отмена/групповое применение, экспорт CSV/XLSX | Реализовано; финальный сквозной сценарий надо повторить |
| Асинхронная очередь | Celery + Redis + Beat, отдельный worker, восстановление и блокировки повторов | Реализовано; worker сейчас отвечает pong |
| Docker Compose | React/nginx, FastAPI, PostgreSQL/pgvector, очередь; миграции 0004 | Работает локально; поставка на другую машину ещё не подтверждена |

Процент — оценка поддержки результата алгоритмом, а не доказанная вероятность.
После ручного выбора и для запомненного решения пользователя значение может быть
пустым: нельзя выдавать придуманную уверенность нейросети. Буквальное «для каждого
товара» стоит пояснить в демонстрации: отделить автоматическую оценку от решения
человека, при необходимости показывать исходную оценку отдельным полем.

## Общие требования

- React SPA, FastAPI REST, PostgreSQL, Celery/Redis и pgvector соответствуют
  перечисленным вариантам стека. Дополнительные Qdrant/RabbitMQ не нужны.
- Профили, задания, ошибки и длительности этапов, результаты и согласия сохраняются
  в PostgreSQL. Подробные технические журналы идут в Docker logs; отдельного полного
  журнала всех событий в PostgreSQL нет. На слайде 5 упомянуто хранение логов в БД:
  описать фактически сохраняемые сведения, не заявлять полный аудит действий.
- PDF >50 страниц без 504: 28.10 синтетический текстовый PDF, 51 страница,
  ответ загрузки за 0,264 с, завершение за 10,611 с. Одна повторённая строка на каждой
  странице не доказывает корректный разбор многостраничных таблиц. Нужен реальный
  PDF через порт 3000 и сверка количества/содержания извлечённых позиций.
- README и Swagger есть. API-раздел README отстал от согласий: для нового аккаунта
  недостаточно входа и загрузки — надо описать регистрацию с версией согласия,
  получение `/api/legal` и подтверждение обработки файлов. Нужен готовый пример
  запросов с cookie, а не только перечень методов.
- Адаптивные стили, обучение, прогресс, ручная проверка и пустой новый аккаунт есть.
  Ранее проверены экраны регистрации/профиля. Полный путь нового пользователя после
  последних изменений в этом аудите не воспроизводился.
- OCR сканов, ЕГРЮЛ, XML/JSON-парсинг закупок, цены, прокси и архивы до 100 МБ
  относятся к другим кейсам. Для кейса 5 они не обязательны по данным презентациям.

## Что блокирует уверенное заявление «готово к сдаче»

1. **Передаваемый комплект.** Каталог `db/ktru_catalog.jsonl.gz` (344098850 байт)
   и `db/ktru_vectors_yandex.npz` (90312482 байта) существуют локально, но исключены
   из Git. Нужны отдельный архив/ссылка, контрольные суммы и проверка доступности.
   Один clone репозитория не запустит готовое решение.
2. **Зафиксированная версия.** Ветка `main`, последний коммит `1ee8f60`, в рабочем
   дереве много изменённых и новых файлов. Текущую рабочую версию нужно проверить,
   сохранить в сдаваемую ветку и передать ссылку на конкретный коммит. Аудит не делал push.
3. **Видео ≤5 минут:** команда, техническое решение и работа приложения — обязательный
   результат этапа 1. В доступных индексируемых файлах проекта видео не найдено;
   наличие у команды вне проекта неизвестно.
4. **Качество атрибутов:** отдельная ручная разметка разнообразных товаров и отчёт
   по каждому полю. Практический минимум для новой проверки — около 100 строк;
   это предложение команды аудита, не число из ТЗ. Не подбирать правила по итоговой
   контрольной выборке. Проверять и отсутствие бренда/модели, и опечатки.
5. **Финальный замер:** новый аккаунт → согласия → 1000 позиций → прогресс → другой
   код вручную → экспорт → проверка содержимого выгрузки. Сохранить время, точность,
   число fallback/words_only, версию модели и коммит. Приёмка сейчас меняет код на
   тот же самый, а экспорт проверяет по HTTP 200 и непустому содержимому: эти
   проверки полезны, но слабее реального сквозного сценария.
6. **Переносимость:** запуск сдаваемого комплекта с пустой базой на другом ПК;
   ранее проверенный чистый Docker-проект на этом ПК был до миграций 0003/0004.

## Что сообщить жюри про нейросети

- Генерация: Yandex AI Studio, `yandexgpt-5.1`, URI
  `gpt://<folder_id>/yandexgpt-5.1`, endpoint `https://ai.api.cloud.yandex.net/v1`.
- Пять настроенных ключей, по одному одновременному запросу; пакет LLM — 10 строк.
  Результат 192,612 с относится к этой конфигурации. Один ключ с другим лимитом
  не гарантирует такое же время; пять ключей сами по себе не увеличивают квоту облака.
- Поиск: Yandex `text-search-query`, каталог заранее рассчитан через
  `text-search-doc`, размерность 256. Требуется отдельный доступ к эмбеддингам.
  Векторы другой модели нельзя подставлять без пересчёта и проверки.
- Ключи не включать в публичный репозиторий. Название модели и настройки вынести
  в README и `.env.example`; каталог передать готовым, не заставлять жюри заново
  оплачивать построение 81509 векторов.
