# Отчёт за вечер 27–28 октября: ktru-lite / «ЕИС Классификатор»

## Что получилось

За вечер проверена вся цепочка приложения, исправлены ошибки поиска и интерфейса,
подключён DeepSeek через Яндекс, снижены расход токенов и время обработки. Затем выполнены
прогоны предоставленных датасетов и создан отдельный набор на 1000 строк с неидеальными
человеческими формулировками.

Основные результаты на этой машине:

- Организаторские 1000 товаров: **182–183 секунды, 970/1000 точных кодов**; правильный код
  присутствует в топ-5 для всех 1000.
- Новый набор на 1000 строк: **234 секунды**. Для 770 строк с сохранёнными требованиями —
  **744 совпадения с исходным кодом (96,6%)**. Неполные и служебные записи оценены отдельно.
- Исправленный эталон на 298 строк: **273/298 (91,6%)**; отдельно на контрольной части —
  **109/120 (90,8%)**.
- Все восемь последних прогонов завершились без ошибок API, резервного извлечения и
  отключения эмбеддингов. Число строк проверено также в CSV/XLSX-выгрузках.

Это интеграция и настройка готовых моделей. Собственную нейросеть с нуля не обучали,
веса DeepSeek/bge-m3 не дообучали. Успешный прогон не означает стопроцентную точность.

Сверены требования кейса 5 из обеих предоставленных презентаций: точность кодов ≥85%,
извлечение атрибутов ≥90%, 1000 позиций менее пяти минут, уверенность, ручная корректировка,
очередь и Docker. Для кодов и времени есть реальные замеры выше. Полнота извлечения именно
брендов и моделей отдельно не доказана; это остаётся проверкой перед защитой.

## 1. Проверка проекта и исходные проблемы

Исходная ревизия — `119f91b`, до начала работ дерево Git было чистым. Используется настоящий
каталог на **81 509 кодов**. Проверены загрузка файлов, извлечение атрибутов, эмбеддинги,
поиск, расчёт уверенности, ручная проверка и экспорт.

Выяснилось, что зелёный статус `llm: on` не доказывает работоспособность каждого ключа.
Старая конфигурация контейнера могла отличаться от уже обновлённого `.env`. Поэтому ключи
проверялись отдельными реальными запросами, а полные прогоны — с учётом источника атрибутов.
Резервные правила и успешные ответы модели в отчётах не смешивались.

Первые проверки с недоступной LLM дали 935/1000 кодов за 167 секунд за счёт локального
извлечения и векторного поиска. Это исходный резервный режим, а не доказательство работы
GigaChat/Gemini и не прямое сравнение скорости одного и того же LLM-режима.

## 2. Что исправлено в backend

### Поиск и выбор кода

- Исправлен случай, когда подбор терял сам тип товара: например, клавиатура попадала в чай,
  а мышь — в мазут. Явное название из каталога возвращается в кандидаты, которые повторно
  ранжируются с настоящими косинусами и прежними правилами характеристик.
- Более конкретные подходящие названия сохраняются. Добавлена защита от чрезмерно общего
  совпадения. Веса ранжирования и пороги уверенности под эти результаты не менялись.
- Ручной поиск фильтрует недействующие коды **до** ограничения выдачи.
- Поиск учитывает границы слов: запрос «стул» больше не находит «фистульный».
- Одноколоночный файл с шапкой «Наименование» больше не создаёт товар из самой шапки.

### Проверка человеком и уверенность

- Ручная замена кода больше не создаёт фиктивную уверенность 100%. Сохраняется
  `confidence=null`, интерфейс показывает «—», экспорт оставляет процент пустым.
- Отмена ручной правки восстанавливает исходный код, оценку и пояснение.
- Режим проверки переходит по `needs_review/failed`, включая возврат к началу списка.
  Обычная навигация по всем строкам сохранена.
- Если известно только короткое название, характеристик и модели нет, а кандидатов несколько,
  позиция требует ручной проверки даже при высокой похожести.
- Автоматический результат не обозначается как уже проверенный человеком.

### Провайдеры и диагностика

- Добавлена поддержка Яндекс AI Studio, отдельных ключей/каталогов и общего ограничения
  параллельности. Пять ключей не считаются автоматическим увеличением квоты одного облака.
- Поддержан прямой DeepSeek API с отключением thinking. Но рабочий маршрут сейчас —
  **DeepSeek V4.1 Flash через Яндекс**, один ключ.
- Добавлены проверки HTTP-контракта, изоляции ключей, семафоров и обработки ответов.
- Диагностика различает отказ OAuth и chat; 401 не объявляется безусловным доказательством
  неверного ключа. Региональный `FAILED_PRECONDITION` ставит провайдера на паузу, вместо
  повторения заведомо неуспешного запроса на каждой пачке.

## 3. Какие модели и ключи проверены

| Вариант | Что выяснилось |
|---|---|
| GigaChat | Сначала старый контейнер возвращал OAuth 401. После обновления окружения реальные ответы работали; полные тесты отличали их от fallback. |
| Google Gemini | Реальный ответ API: регион не поддерживается (`FAILED_PRECONDITION`). Успешный статус общей LLM не выдавался за успешный Gemini. |
| Первый и третий ключи Яндекса | На момент последних отдельных проверок — 403 PermissionDenied. Конкретная административная причина по этому ответу не установлена: нужно проверять права и биллинг. |
| Второй ключ Яндекса | Исправлен folder ID согласно ответу API, после этого запросы работали. Этот ключ используется сейчас. |
| Прямой DeepSeek | Ключ считывался, но API возвращал 402 из-за недостаточного баланса. Этот маршрут сейчас не выбран. |
| DeepSeek через Яндекс | Проверен отдельным запросом и затем полными датасетами. Отдельный баланс прямого DeepSeek не нужен; потребление учитывает Яндекс. |

Ключи в этот отчёт и Git не включены. `.env` остаётся локальным.

## 4. Как ускорена и удешевлена обработка

### Устранён неверный таймаут для больших пачек

Один товар обрабатывался успешно, но 20 товаров требовали около **56 секунд**, тогда как
backend прерывал запрос через 40 секунд. Из-за этого весь первый массовый тест уходил в
резервные правила. Причина была в настройке, а не в предоставленном ключе.

Пачки уменьшены до пяти товаров, ожидание одного запроса — 60 секунд. Число повторов
ограничено, чтобы не тратить несколько длинных запросов при сбое.

### Компактный ответ модели

Вместо повторения длинных ключей JSON, пустых полей и полного поискового текста модель
возвращает короткие поля и тройки характеристик. Backend восстанавливает обычный формат
атрибутов и проверяет значения по исходной строке. Отдельный модуль — `backend/attribute_format.py`.

На одинаковых 100 строках:

| Показатель | До | После |
|---|---:|---:|
| Полное время | 140 с | 47 с |
| Точные коды | 96/100 | 96/100 |
| Выходные токены, включая второе мнение | 21 407 | 9 519 |
| Оценка стоимости до скидок | 19,13 ₽ | 12,41 ₽ |

Выигрыш времени включает переход с двух на четыре параллельных запроса **через один ключ**.
Первый компактный эксперимент потерял один правильный код из-за слишком короткой категории;
этот вариант не применялся. Сохранение полного уточнённого названия исправлено и проверено
повторным реальным прогоном.

### LLM вызывается только там, где нужна

Строки с точным названием из каталога и явными полями «характеристика: значение» разбираются
локально. Неизвестные названия, свободный текст, бренды и модели остаются DeepSeek.
Источник локальных атрибутов — `structured`: это штатный маршрут, не скрытый сбой модели.

В организаторском наборе 856 строк разобраны локально, 144 — DeepSeek. Векторный поиск
выполняется для каждой строки. Дополнительно устранена повторная передача характеристик
в локальную bge-m3: полный исходный текст уже содержал все эти значения.

На полном наборе из 1000 товаров это дало **183 секунды и 970 точных кодов**. Укорочение
текста эмбеддингов изменило отдельные результаты: восемь ошибок исправились, семь ранее
правильных ответов стали неправильными. Итоговая точность выросла на один товар; улучшение
каждой отдельной позиции не заявляется.

Повторяющиеся строки внутри задания уже объединялись в исходном коде. Это проверено тестом,
но не выдаётся за новую написанную с нуля оптимизацию. Между разными заданиями ответы LLM
не кэшируются. Общий кэш эмбеддингов влияет на повторные измерения.

## 5. Что исправлено в интерфейсе

- Ошибки истории заданий, каталога и поиска отделены от пустой выдачи, добавлен повтор загрузки.
- Старые результаты не остаются видимыми при смене запроса; исправлены устаревающие ответы
  внутри карточки позиции и проверки ручного кода.
- В результатах видно исходное название; длинное имя файла доступно в подсказке истории.
- Массовое принятие явно описано как действие по всей спецификации независимо от фильтров.
- Убрано глобальное уменьшение интерфейса через `zoom: .9`, подпись выгрузки видна на desktop.
- Обучающий тур открывается по кнопке, не запускается автоматически.
- Проверены отдельные сценарии в браузере: фильтр отменённых кодов, ошибка каталога, неизвестный
  маршрут, начало проверки, переход вниз и выход по Esc с восстановлением фокуса.

Полная проверка всех размеров экранов и всех клавиатурных сценариев пока не заявляется.

## 8. Проверки и запуск для команды

Последний полный backend-прогон: **160 passed, 10 skipped**, ruff check и format прошли.
Пропущенные проверки не объявляются успешными. Перед публикацией ветки повторно прошли
все эти backend-проверки, frontend lint, сборка и тест API-транспорта (1 passed).
Основной backend после применения настроек: каталог ready, 81 509 кодов, эмбеддинги и LLM on.
Пользовательские задания и Docker volumes сохранены; аудит использовал отдельную SQLite-базу.

Для запуска:

1. Взять эту ветку. Положить прежний дамп в `db/ktru_catalog.jsonl.gz`: сам каталог не менялся
   и в Git не загружался.
2. Если `.env` ещё нет — скопировать `.env.example`. Существующий `.env` не перезаписывать.
3. Заполнить `YANDEX2_API_KEY` и соответствующий `YANDEX2_FOLDER_ID`. Шаблон настроен на
   `LLM_PROVIDERS=yandex2`, `deepseek-v4.1-flash/latest`, reasoning none, четыре потока,
   пачки по пять, компактный и структурированный режимы.
4. Выполнить `docker compose up -d --build`. Проверка одного ключа:
   `docker compose run --rm --no-deps backend python check_llm.py yandex2`.
5. Открыть `http://localhost:3000`, загрузить файл и проверить выгрузку.

Четыре потока проверены на текущем аккаунте, квота другого аккаунта может требовать двух.
При смене `.env` backend нужно пересоздать после завершения активных заданий.
Секреты, экспорт Telegram, служебные preview/логи и временные результаты в ветку не включены.
Компактные метрики и ошибки доступны в [eval/reports/2026-10-28](../eval/reports/2026-10-28/summary.json).

## 9. Что ещё осталось и что не нужно обещать на защите

- Время менее пяти минут подтверждено на проверенных файлах и этой машине после готовности
  сервиса. На неизвестном железе, при холодном запуске и другом составе описаний нужен замер.
- Полнота распознавания брендов и моделей на разнообразных реальных товарах не доказана
  эталоном из каталожных описаний. Не заявляем универсальные 90% для всех атрибутов.
- Уверенность не равна гарантии правильности; нужна дальнейшая независимая калибровка.
- Разбор сканированных PDF с OCR и все адаптивные/клавиатурные сценарии полностью не проверены.
- Очередь сейчас PostgreSQL, поиск — NumPy/BM25 и bge-m3. Celery/Redis и pgvector/Qdrant
  не добавлялись: если общий стек из презентации обязателен буквально, это надо закрыть отдельно.
- Для двух неработавших ключей Яндекса нужны административные проверки прав/биллинга.
  Текущий рабочий режим от них не зависит.
- Ветка подготовлена для командного ревью. Изменения в `main` не сливались.
