## Общие требования и сценарий

- React SPA, FastAPI REST, PostgreSQL, Celery/Redis и pgvector реально используются.
  Нужен один из перечисленных вариантов в каждом слое; добавлять одновременно
  RabbitMQ, Qdrant и Pinecone не требуется.
- XLSX/CSV/PDF поддержаны parser.py. Технические характеристики извлекаются,
  отображаются и участвуют в ранжировании. Приёмочный порог ≥90% на слайде 23
  перечисляет название, бренд и модель; отдельная метрика характеристик там не задана.
- PDF на 51 странице: HTTP 202 за 0,264 с, завершение за 10,611 с. Это специально
  созданный текстовый файл с одинаковой строкой Notebook 16 GB на каждой странице.
  Он проверяет асинхронную обработку >50 страниц, а не качество разбора сложной
  закупочной спецификации. Живой замер шёл через HTTP API; большой PDF через
  frontend/nginx отдельно в этой сверке не прогонялся.
- Для кейса 5 не заявлены OCR ≥95%, архивы 100 МБ, анализ рисков, ЕГРЮЛ и поиск
  цен: это требования других кейсов. Ограничение текущего приложения — 10 МБ,
  200 страниц текстового PDF и 1000 позиций; его следует явно показать в инструкции.
- Короткий README, Swagger, карта архитектуры, миграции и инструкция подготовки
  обоих каталоговых файлов есть. В README описаны методы и JSON ручной правки,
  но для передачи удобно добавить полностью готовые команды загрузки/входа.
- Полноценная проверка понятности и адаптивности интерфейса с новым пользователем
  и на узком экране в этой сверке не выполнялась.
- Дамп 344098850 байт и NPZ 90312482 байт существуют локально, но исключены из Git.
  Чистому получателю нужен архив с обоими файлами и настроенные ключи. Один clone
  репозитория без данных и настроек не является готовой поставкой.
- В рабочем дереве много незакоммиченных изменений. Эта сверка не создавала commit
  и не делала push; готовность удалённой ветки к сдаче не подтверждена.
- Видео команды/решения/приложения ≤5 минут обязательно на слайде 7. В доступных
  файлах проекта видео не найдено; готовность видео у команды не подтверждена.

## Приоритет перед сдачей

1. Закрыть буквальное требование процента для каждого автоматически предложенного
   кода, включая второе мнение; определить осмысленную оценку, а не подставлять
   число для вида. Приёмка сейчас допускает confidence=None — этого недостаточно
   для проверки данного пункта ТЗ.
2. Проверить название/бренд/модель на отдельной разметке хотя бы 100 разнородных
   строк: свободный текст, пропуски бренда/модели, опечатки, разные категории.
   Это план проверки, число 100 не взято из ТЗ. Оценивать поля отдельно и показать
   ошибки; не использовать эту же выборку для подбора правил и итоговой оценки.
3. Прогнать реальный текстовый PDF >50 страниц через frontend, проверить количество
   и содержание товаров; пройти загрузку → результат → исправление → экспорт в UI.
4. Подготовить переносимую поставку с обоими файлами каталога, проверкой контрольных
   сумм и понятной настройкой API. Запустить на другом компьютере; сохранить отчёт.
5. Сохранить проверенный код в сдаваемую ветку и подготовить видео ≤5 минут.

Новая перестройка архитектуры для этого не нужна. Перед сдачей важнее закрыть
перечисленные расхождения и собрать воспроизводимые доказательства.
