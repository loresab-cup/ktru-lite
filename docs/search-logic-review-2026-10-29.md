# Логика подбора КТРУ: ревью 29.10.2026

Статус: три контрпримера ниже исправлены. Это исходное ревью до исправлений;
итоговые изменения и контрольное сравнение — в [отчёте](search-fixes-2026-10-29.md).

## Вывод

Основа подходит задаче: извлечение атрибутов → эмбеддинги → точный pgvector-поиск
с добавлением BM25-кандидатов → сравнение характеристик → top-5 → уверенность →
второе мнение только для спорных строк. Это гибридный поиск с проверяемыми
правилами. Новая архитектура или ещё одна большая модель не нужны.

Главный риск — уверенность и автоматический выбор при недостаточной или
противоречивой информации. Ранжирование обросло частными поправками, поэтому
добавлять новые веса без контрольного набора опасно.

## Подтверждённые контрпримеры

Проверены офлайн в Docker на синтетическом каталоге, без внешних API. Скрипт:
outputs/search-logic-review/reproduce.py. Частота этих случаев в реальных данных
не измерялась; это доказательство возможности, не оценка общей точности.

1. **Слабое совпадение получает высокий процент.** confidence.assess для активных
   кандидатов с score=0.40 и 0.35, is_product=True выдаёт confidence=99.9 и status=auto.
   Формула сильно зависит от отрыва; абсолютная слабость совпадения и явные
   противоречия не запрещают автоматический выбор. Код: confidence.py, probability/assess.
2. **Числа разных характеристик смешиваются.** _numeric_fit для запроса
   «оперативная память 16 ГБ» и границы, полученной из характеристики SSD 16 ГБ,
   возвращает (1,0). numeric_bounds сохраняет диапазон/единицу, но теряет имя
   характеристики; единица bytes не отличает RAM от SSD. Код: characteristics.py
   numeric_bounds, search.py _numeric_fit. Это ложный бонус, не доказательство,
   что весь поиск обязательно ошибётся: остальные признаки могут компенсировать его.
3. **Жёсткий якорь первого слова может удалить верного кандидата.** В каталоге
   из «Ноутбук» и «Средство для мытья посуды», при правильном первоначальном
   результате «Ноутбук», _anchored для «Для офиса: ноутбук, 16 ГБ» возвращает
   только средство для посуды. После такого ограничения второму мнению уже
   неоткуда выбрать ноутбук. Код: search.py _anchored/_anchored_word.

## Улучшения с минимальной сложностью

1. Отделить выбор лучшего кандидата от разрешения auto. При недостатке данных,
   конфликте обязательных характеристик или слабом соответствии типа товара
   оставлять needs_review. Порог слабого совпадения подобрать измерением,
   не назначать произвольно.
2. Сравнивать структурированное «название характеристики + значение + единица».
   Уже извлечённые характеристики доступны; не нужен новый LLM-вызов. Если имя
   не сопоставлено уверенно, число не должно давать сильное подтверждение.
3. Не заменять весь набор кандидатов по служебному первому слову. Якорь должен
   опираться на установленный тип товара, сохранять семантические альтернативы
   и не превращать предлоги/вводные фразы в обязательный товарный признак.
4. После изменения ранжирования заново оценить уверенность на отдельном наборе.
   Сейчас коэффициенты подбирались по 1000 строкам и их изменённой копии; это
   не подтверждает калибровку на новых категориях. Измерять ошибку среди auto,
   долю auto и соответствие процентов фактической точности по интервалам.
5. Сначала закрыть эти три случая тестами и сделать офлайн-replay старых ответов.
   Потом один живой контрольный прогон. Не увеличивать число моделей и не
   добавлять очередные частные коэффициенты вместо устранения причины.

## Скорость и измерения

Сохранённый parallel-auto.json от 29.10: 1000 строк, 989 точных кодов,
103.266 с, fallback=0, words_only=0. В fresh-one-key.json отражён отдельный
одноключевой прогон около 201 с. Это исторические одиночные измерения при своих
квотах, а не гарантия для произвольной одновременной нагрузки.

Новые проверки характеристик и условий auto выполняются локально, дополнительных
сетевых запросов не требуют. Их влияние на время надо измерить. Точный pgvector
пока оставить: приблизительный индекс требует отдельной проверки полноты кандидатов.
Кеш результатов поиска можно рассмотреть для повторяющихся строк, с ключом,
включающим версию каталога, текст, якорь, единицы и include_inactive. Эмбеддинги
и LLM-извлечение уже имеют кеширование/дедупликацию — не дублировать их вслепую.

Приёмка улучшения: >=85% точных кодов по ТЗ без ухудшения прежних наборов,
1000 строк <300 с от загрузки до завершения; отдельно время очереди, fallback,
words_only, top-5 recall, доля auto и число неверных auto. Проверить также
неполные описания и товары, которых в каталоге нет. В human-наборе прежний
отчёт содержит 66 auto на 200 неоднозначных строк: это требует разбора,
но само по себе не означает, что все 66 кодов неправильные.

Исходники в рамках этого ревью не изменялись. Исправления требуют отдельного
цикла измерений; обещать сохранение 103 с до такого цикла нельзя.
