# КТРУ-классификатор

Сайт для кейс-чемпионата B2B-РТС (задача 5). Пользователь загружает спецификацию закупки
(xlsx, csv, docx, pdf или txt). Система достаёт из каждой строки наименование, бренд, модель и
характеристики, подбирает код каталога КТРУ и считает уверенность в процентах. Спорные позиции
человек проверяет и при необходимости правит, потом выгружает результат в xlsx или csv.

Этот файл написан для того, кто будет разбираться в коде. Сначала общая картина, потом каждый
модуль по отдельности, потом рецепты для типовых правок. Прежний README с историей решений и
замерами лежит в [docs/notes-and-measurements.md](docs/notes-and-measurements.md).

## 1. Что внутри, в двух словах

Три контейнера в одном `docker-compose.yml`:

- `frontend`: nginx со статикой React и прокси на backend. Порт 3000.
- `backend`: FastAPI на Python 3.12. Принимает файлы, держит очередь заданий, считает коды.
- `db`: PostgreSQL 16. Таблицы `jobs` и `items`.

Векторы текста (256 чисел) считает Yandex AI Studio по сети, локальных моделей нет.

Работа над одной строкой спецификации идёт так:

```
строка файла
   |  parser.py       разбор файла в строки
   v
нейросеть (YandexGPT, запасной GigaChat) достаёт наименование, бренд, модель, характеристики
   |  extractor.py + providers.py
   v
вектор строки (Yandex AI Studio, text-search-query)
   |  embedder.py
   v
поиск по каталогу из 81 509 кодов: косинус, BM25, правила ранжирования
   |  search.py
   v
пять кандидатов, уверенность в процентах, статус
   |  confidence.py
   v
спорные строки перепроверяет нейросеть, выбирая из пяти кандидатов
      chooser.py
```

Два момента, которые важно понимать сразу.

Нейросетям не доверяют. Всё, что они вернули (наименование, бренд, значения), проверяется:
значение остаётся, только если оно дословно есть в исходной строке. Если нейросеть недоступна,
атрибуты берутся простыми правилами, и задание всё равно заканчивается.

Код выбирает не нейросеть, а поиск по каталогу. Нейросеть извлекает атрибуты и в конце даёт
второе мнение по спорным строкам, но только из тех пяти кодов, которые уже нашёл поиск.
Придумать несуществующий код она не может.

## 2. Запуск

### Что нужно

- Docker Desktop (на Windows с WSL 2) или Docker Engine с Compose v2.
- Дамп каталога `db/ktru_catalog.jsonl.gz` (около 344 МБ). В git его нет, положите файл в
  папку `db/`. Каталог берётся из справочника организаторов, с сайта ЕИС его не парсили.
- Около 6 ГБ диска и 4 ГБ свободной памяти.
- Файл векторов каталога `db/ktru_vectors_yandex.npz` (около 90 МБ, тоже не в git). Где его
  взять или как построить, сказано в разделе «Векторы каталога». Без него каталог не
  загружается, на главной плашка «Каталог не загружен», а `/api/health` пишет причину в `catalog_error`.
- Интернет при первой сборке (образы, пакеты) и для запросов к нейросетям и векторам.

### Одна команда

```bash
docker compose up -d --build
```

Сайт откроется на [http://localhost:3000](http://localhost:3000). Документация API на http://localhost:8000/api/docs
доступна только с этого компьютера. Первая сборка занимает 5-10 минут. Каталог после старта
загружается около 20 секунд, пока идёт загрузка, на главной плашка «Каталог загружается».

Без `.env` всё запустится, но нейросетей не будет: атрибуты извлекаются правилами, а коды
ищутся только по словам, точность заметно ниже. Об этом говорят плашки на главной.

### Настройка `.env`

```bash
cp .env.example .env
```

В `.env` нужно вписать:

1. Ключи нейросетей. `LLM_PROVIDERS=yandex,yandex2,yandex3,yandex4,yandex5,gigachat` задаёт
   список и порядок. Для первого ключа YandexGPT нужны `YANDEX_API_KEY` и `YANDEX_FOLDER_ID`
   (каталог в Yandex Cloud), для остальных только строка `YANDEXn_API_KEY`: каталог, модель и
   число потоков берутся из блока `YANDEX_*`. Ключ из другого облака приносит свой
   `YANDEXn_FOLDER_ID`. Для GigaChat нужен `GIGACHAT_CREDENTIALS`.
2. Ключ векторов Яндекса `YANDEX_EMBED_API_KEY` и каталог `YANDEX_EMBED_FOLDER_ID`, см. ниже.
   Без них поиск идёт только по словам.

### Векторы каталога

Строки спецификации и коды каталога превращаются в векторы моделями Yandex AI Studio
(`text-search-query` для строк, `text-search-doc` для каталога, 256 чисел). Видеокарта и
локальные модели не нужны. Сервисному аккаунту ключа нужна роль на нейросети Yandex AI Studio в
каталоге `YANDEX_EMBED_FOLDER_ID` (например, `ai.languageModels.user`), иначе Яндекс отвечает
403 PermissionDenied.

Векторы каталога лежат в `db/ktru_vectors_yandex.npz` (90 МБ, в git его нет, как и дампа).
Готовый файл можно взять у команды: строить его заново не нужно. Если файла нет, его строят один
раз: 81 509 кодов, но 77 610 разных текстов (у 3 899 кодов текст совпадает с другим кодом, такой
текст спрашивается один раз), около 70 рублей. Квота считается на облако: 28.10.2026 одно облако
держало 24 запроса в секунду без отказов (около 55 минут на каталог), два облака — 56 в секунду
(около 23 минут). Ключ второго облака даётся только скрипту, сайт его не использует; одна и та же
модель в разных облаках даёт одинаковые векторы. Скрипт можно прервать, новый запуск продолжит с
места остановки. Backend без файла не загружает каталог, но работает, поэтому скрипт запускается
в его контейнере:

```bash
docker compose cp scripts/embed_catalog.py backend:/tmp/embed_catalog.py
docker compose exec -d -e YANDEX_EMBED_RPS=25 backend sh -c "python /tmp/embed_catalog.py /catalog/ktru_catalog.jsonl.gz /cache/ktru_vectors_yandex.npz > /cache/embed.log 2>&1"
docker compose exec backend tail -3 /cache/embed.log
docker compose cp backend:/cache/ktru_vectors_yandex.npz db/
docker compose restart backend
```

С ключом второго облака добавьте к команде скрипта
`--accounts YANDEX_EMBED_API_KEY:YANDEX_EMBED_FOLDER_ID,YANDEX_API_KEY:YANDEX_FOLDER_ID` (имена
переменных, не значения).

Векторы каталога сделаны по `embedding_text` из дампа. В дампе есть и старое поле
`embedding_b64` (векторы bge-m3 прежней схемы); оно больше не читается, по нему только
отбираются коды, для которых строился файл векторов.

Замеры 28.10.2026, живой прогон всех наборов через сайт (`scripts/bench.py`), пять ключей
YandexGPT 5.1, векторы Яндекса. В скобках прогон того же дня до правок финала (порядок слов в
названии, векторы в фоне):

| Набор | Точный код | Авто, строк | Неверных в авто | Время |
| --- | ---: | ---: | ---: | ---: |
| реальная спецификация, 12 | 12 (12) | 8 (8) | 0 (0) | 11 с (11) |
| форма ЕИС и её копия, 3 + 3 | 3 и 3 (3 и 3) | 3 и 3 (3 и 3) | 0 (0) | 3–4 с |
| пример сайта, 11 | 11 (11) | 10 (9) | 0 (0) | 9 с (10) |
| 292 строки | 292 (292) | 271 (271) | 0 (0) | 77 с (69) |
| 292 изменённые | 289 (285) | 260 (258) | 0 (3) | 84 с (82) |
| 1000 строк | 981 (981–982) | 825 (822–824) | 2 (2) | 222 с (211–218) |
| 1000 изменённые | 978 (974) | 801 (799) | 2 (6) | 238 с (227) |
| human_1000, 770 строк с кодом | 752 (753) | 663 (663) | 3 (3) | 214 с (209) |

Прежняя схема (bge-m3 в Ollama на видеокарте RTX 5070, утро 28.10) давала точный код 972 и 965 на
тысячах строк, 289 на 292 изменённых, в авто 883 и 869 строк при 7 и 7 неверных; её цифры и
история в [docs/final-report-2026-10-28.md](docs/final-report-2026-10-28.md). В шкале Яндекса
косинус почти не отличает верный код от неверного, решает отрыв от второго кандидата, поэтому
веса уверенности подобраны заново (`confidence.py`). Каждая строка спецификации — отдельный
запрос векторов (платно, 0,0101 рубля за 1000 токенов), `docker-compose.yml` ставит 20 запросов в
секунду.

После правки `.env` выполните `docker compose up -d --build` ещё раз. Проверить ключи можно так:

```bash
docker compose exec backend python check_llm.py
```

Каждому провайдеру положено ответить `OK за N с`. Если нет, скрипт подскажет причину: 401 это
ключ, 402 баланс, 404 модель или адрес, 429 слишком много потоков.

### Пользователи

Без входа сайт показывает только страницу с двумя вкладками: «Вход» и «Регистрация». Любой
посетитель регистрируется сам: логин (3–32 знака, латинские буквы, цифры, точка, дефис,
подчёркивание, без учёта регистра) и пароль не короче 8 знаков, введённый дважды. После
регистрации он сразу на сайте. Все пользователи видят все спецификации.

Учётками можно управлять и из командной строки; пароль команда спрашивает дважды и не показывает:

```bash
docker compose exec backend python users.py list
docker compose exec backend python users.py passwd ivan    # новый пароль закрывает все входы
docker compose exec backend python users.py remove ivan
```

`users.py add <логин> [--admin]` добавляет пользователя. Если пользователей ещё нет, backend при
старте создаёт администратора из `ADMIN_LOGIN` и `ADMIN_PASSWORD` в `.env` (необязательно). Для
разработки без входа есть `AUTH_REQUIRED=0`; на сервере его не ставьте.

### Остановить, перезапустить, сбросить

```bash
docker compose stop              # остановить, данные остаются
docker compose up -d             # запустить снова
docker compose logs -f backend   # лог обработки: какой провайдер, сколько секунд
docker compose down -v           # удалить контейнеры и все данные
```

## 4. Архитектура

### Контейнеры и порты

```
браузер
   |  http://localhost:3000
   v
frontend (nginx, порт 8080 в контейнере)
   |  /            статика React, любой неизвестный адрес отдаёт index.html
   |  /api/*       прокси на backend:8000
   v
backend (FastAPI)  ----->  db (PostgreSQL)      jobs, items
   |
   +------------------->  YandexGPT, GigaChat,   внешние нейросети по HTTPS
                          векторы Yandex AI Studio
```

Порты наружу: 3000 (сайт) и 127.0.0.1:8000 (API и документация, только с этого компьютера).
Данные лежат в томах: `pgdata` (база), `cache` (кэш метаданных каталога), `uploads` (загруженные
файлы до конца обработки). Каталог монтируется из `./db` только для чтения.

### Очередь без Redis

Очередью служит таблица `jobs`. При запуске backend поднимает `WORKERS` потоков (по умолчанию 2).
Каждый поток раз в секунду пробует взять задание со статусом `queued`:

```sql
SELECT id FROM jobs WHERE status = 'queued' ORDER BY created_at LIMIT 1
FOR UPDATE SKIP LOCKED
```

После выбора идёт условный `UPDATE ... WHERE status = 'queued'`: если задание успел взять другой
поток, обновится ноль строк, и этот поток пойдёт дальше. Пока файл обрабатывается, число готовых
строк пишется в `jobs.processed`, по нему интерфейс рисует прогресс. Если backend перезапустили
посреди работы, задания со статусом `processing` при старте возвращаются в `queued` и
обрабатываются заново с начала (`init_db`).

### Два вида нейросетей

Обе внешние. YandexGPT (запасной GigaChat) разбирает текст строки на атрибуты. Модели векторов
Yandex AI Studio только считают векторы: строки `text-search-query`, каталог заранее
`text-search-doc`. Векторы каталога и строк должны быть одной модели, поэтому `api.load_catalog`
не принимает файл векторов другого размера.

### Каталог в памяти

Весь каталог (81 509 кодов, вектор 256 float32 у каждого, около 83 МБ) хранится в памяти
backend. Поиск это умножение матрицы запросов на матрицу каталога, то есть точный косинус без
приближений. Приближённый индекс (HNSW) пробовали, он терял до 14 процентов верных кодов.
Первый старт читает дамп (около 20 секунд) и пишет метаданные в `CACHE_DIR`, следующие старты
берут кэш; векторы каждый раз читаются из `db/ktru_vectors_yandex.npz` за секунды.

## 5. Путь одного файла

Что происходит от нажатия «Обработать» до выгрузки, по шагам и с названиями функций.

1. Браузер отправляет файл на `POST /api/jobs` (`create_job` в `routes/jobs.py`). Backend читает не
   больше 10 МБ плюс один байт, проверяет, что файл не пустой и что начало файла соответствует
   расширению (`parser.check_signature`). Файл сохраняется на диск под именем `<uuid>.<ext>`,
   имя пользователя на диск не попадает. В таблицу `jobs` пишется запись со статусом `queued`.
   Ответ 202 с идентификатором задания.
2. Интерфейс переходит на `/jobs/<id>` и раз в секунду спрашивает `GET /api/jobs/<id>`.
3. Свободный воркер берёт задание (`claim_job`) и запускает `run_job`.
4. `parser.parse_file` читает файл и возвращает список `Item(row_number, text, columns)`.
   Строк не больше 1000.
5. Создаётся `extractor.JobExtractor`. Он режет уникальные тексты на пачки по `LLM_BATCH` строк
   (в рекомендуемом `.env` — 10; без настройки — 20) и сразу отдаёт первые пачки в общий пул потоков, не больше одного круга
   по числу слотов всех провайдеров. Пока одна пачка ждёт ответа, остальные уже летят.
6. `process_items` идёт по строкам файла пачками по 20 (`BATCH` в `runtime.py`). Для каждой пачки
   `process_batch`:
   - берёт атрибуты у `JobExtractor` (`llm.get`), при необходимости ждёт;
   - собирает запрос для поиска: `search_text` из нейросети плюс исходный текст строки;
   - определяет единицу измерения: из колонки «Ед. изм.» файла и из догадки нейросети;
   - считает векторы (`embedder.embed`) и ищет кандидатов (`Catalog.search`);
   - превращает результат в записи `Item` (`build_item`: код, уверенность, зона, статус,
     пояснение) и пишет их в базу одной транзакцией;
   - обновляет `jobs.processed`.
     Поэтому готовые карточки появляются в интерфейсе по двадцать штук, пока остальные считаются.
7. Когда все строки обработаны, `choose_codes` берёт позиции со статусом `needs_review` и
   отдаёт нейросети на второе мнение (`chooser.choose`). Код меняется, только если нейросеть
   выбрала другой код из тех же пяти кандидатов. Уверенность и статус при этом не трогаются:
   строка всё равно остаётся на проверку человеку.
8. `finish` ставит статус `done`, время этапов (`stage_seconds`) и удаляет загруженный файл.
9. Человек открывает карточки, принимает или исправляет коды. Каждое действие это отдельный
   запрос к `/api/items/...`.
10. «Выгрузить» открывает `GET /api/jobs/<id>/export`, backend собирает xlsx или csv из таблицы
    `items`.

Остановка (`POST /api/jobs/<id>/cancel`) ставит статус `cancelled` и взводит `threading.Event`
этого задания. Очередь пакетов к нейросети снимается, воркер выходит из цикла между пачками.
Уже обработанные позиции остаются, их можно проверить и выгрузить.

## 6. Backend по модулям

### api.py

Небольшая точка сборки FastAPI. Маршруты разделены в `routes/`, подключение — в
`database.py`, модели — в `models.py`, настройки и состояние — в `runtime.py`.
Очередь хранится в PostgreSQL (`job_store.py`), фоновые циклы — в `workers.py`,
обработка позиций — в `pipeline.py`. Полная карта: [структура backend](docs/backend-structure.md).

Блок очереди:

- `claim_job`: взять задание из очереди (см. раздел 4).
- `run_job`: основной цикл обработки одного задания. Читает файл, запускает `process_items`,
  потом `choose_codes`, в конце `finish`. Любое исключение превращается в понятный статус
  `failed` с текстом для пользователя. После завершения файл удаляется.
- `process_items` и `process_batch`: пачки по 20 строк, описаны в разделе 5.
- `apply_candidates`: из списка кандидатов выставляет код, название, уверенность, зону, статус и
  пояснение позиции. Её же использует правка атрибутов.
- `build_item`: создаёт `Item`. Если на строке случилась ошибка, позиция получает статус
  `failed`, но задание продолжается.
- `choose_codes`: второе мнение. Меняет код через условный `UPDATE`, который сработает только
  если позиция всё ещё `needs_review` с тем же кодом, так что правки человека во время
  обработки не затираются.
- `finish`: итоговый статус. Остановленное задание остаётся остановленным, даже если воркер
  дописал позже.
- `worker_loop`, `load_catalog`, `init_db`, `lifespan`: запуск и остановка.

Эндпоинты описаны в разделе 8. Некоторые детали, которых нет в таблице:

- `get_job` кроме полей задания отдаёт `counts` (сколько позиций в каждом статусе), `fallback`
  (у скольких строк атрибуты получены правилами, а не нейросетью) и `words_only` (у скольких
  строк код искали только по словам, потому что векторы Яндекса не ответили).
- `list_jobs` отдаёт те же `counts` для каждого задания одним запросом и общее число заданий в
  заголовке `X-Total-Count`.
- `list_items` умеет фильтровать по статусам через запятую, искать по тексту строки, коду и
  названию (без учёта регистра, спецсимволы `%` и `_` экранируются), и по флагу
  `candidates=false` не отдаёт пять кандидатов. Они нужны только странице позиции, а весят около
  10 КБ на строку. Сортировка: `sort=code|confidence|status` и `order=asc|desc` (по статусу
  сначала «Нужна проверка», потом ошибки, авто, исправленные, принятые); без `sort` порядок как в
  файле.
- `get_item` возвращает позицию и её место в задании: `position`, `total`, `prev_id`, `next_id`,
  `next_unreviewed_id` (следующая позиция, не принятая и не исправленная). У каждого кандидата
  есть `confidence` (какой была бы уверенность, будь он выбран) и `differs`: до четырёх
  характеристик, значения которых у кандидатов разные. Так видно, чем отличаются пять кодов с
  одним названием («Мыло туалетное твердое» отличаются маркой мыла).
- `correct_item` принимает код с пробелами и переносами, проверяет его по каталогу и ставит
  статус `corrected`, уверенность 100.
- `edit_attributes` принимает исправленные наименование, бренд, модель и характеристики, строит
  новый поисковый запрос, ищет заново и обновляет код. Исходные колонки файла сохраняются.
- `accept_item` и `accept_job`: принять один код или все коды выше порога уверенности. Массово
  принимаются только действующие коды и только строки, похожие на товар.
- `undo_code` (`POST /api/items/{id}/undo-code`): вернуть код, который был до последней ручной
  смены. Перед каждой сменой кода (`PATCH` или правка атрибутов) снимок кладётся в
  `attributes.history`, хранится до 10 шагов.
- `revert_items` (`POST /api/jobs/{id}/revert`): вернуть на проверку выбранные принятые и
  исправленные позиции (`{"ids": [...]}`) или все принятые (`{"all_accepted": true}`).
- `revert_item` отменяет принятие или ручной код. Для этого перед первым изменением в
  `attributes.original` сохраняется снимок: код, название, уверенность, зона, статус, пояснение.
  `revert` восстанавливает снимок и удаляет его. Если позиция была принята до появления снимков,
  код остаётся, а уверенность, зона и статус пересчитываются по кандидатам.
- `delete_job` удаляет позиции, задание и файл. Задание в обработке удалить нельзя (409).
- Выгрузка: `export_rows` собирает таблицу. К колонкам исходного файла добавляются
  наименование, бренд, модель, характеристики, код, название кода, уверенность, статус кода и
  статус позиции. Функция `cell` ставит апостроф перед текстом, который начинается с `=`, `+`,
  `-` или `@`, чтобы Excel не принял ячейку за формулу. CSV пишется с разделителем `;` и BOM
  (`utf-8-sig`), чтобы Excel открыл кириллицу. Колонка `candidates` при выгрузке из базы не
  читается (`defer`).

### parser.py

Превращает файл в список позиций `Item(row_number, text, columns)`. `text` это строка, которая
пойдёт нейросети и поиску, `columns` все исходные колонки для выгрузки.

Что делает для каждого формата:

- xlsx: читает все листы в режиме `read_only`, проверяет, что внутри не zip-бомба (не больше
  200 МБ после распаковки) и ячеек не больше 300 тысяч.
- csv: кодировка utf-8 или cp1251, разделитель определяется (`;`, `,` или табуляция).
- docx: сначала таблицы, если их нет, то абзацы.
- pdf: текст не больше 200 страниц, каждая строка текста это позиция.
- txt: каждая непустая строка это позиция.

Как найти нужные колонки в таблице (`parse_rows`): сначала ищется строка заголовка среди первых
тридцати (в ней должны быть слова вроде «наименование», «товар», «характеристик», «количество»).
Колонка с наименованием определяется по заголовку, а если его нет, берётся колонка с самым
длинным текстом. Колонки со словами «характеристика», «бренд», «марка», «модель»,
«производитель», «описание» присоединяются к тексту позиции. Служебные колонки (инструкция,
обоснование, национальный режим) в текст не попадают. Пустые строки, «Итого» и строки-повторы
заголовка пропускаются.

Отдельно разобрана форма ЕИС «Описание объекта закупки» (`parse_eis_rows`): там товар занимает
несколько строк таблицы, по одной характеристике на строку, а «№» и наименование заполнены
только в первой. Такие строки склеиваются в одну позицию, единица измерения товара добавляется
в конец текста.

Ограничения (`MAX_*` в начале файла): 10 МБ файл, 1000 позиций, 2000 символов в ячейке. Ошибки,
которые должен исправить пользователь, это `ParseError` с готовым русским текстом.

### extractor.py

Достаёт из текста строки структуру: `name`, `brand`, `model`, `characteristics`
(`name`, `value`, `unit`), `search_text` и `measure` (единица, в которой такой товар обычно
закупают).

Системный промпт (`SYSTEM_PROMPT`) говорит нейросети, что сообщение пользователя это данные, а
не инструкции. Строки уходят JSON-массивом `[{id, text}]`. Это защита от строк, в которых
написано что-то вроде «забудь инструкции».

Главная защита `accept`: значение из ответа принимается только если оно дословно встречается в
исходной строке (после приведения к нижнему регистру, замены `ё` на `е` и сжатия пробелов).
Исключения: `search_text` и `measure` это подсказки для поиска, их по строке не проверяют.
Если наименование нейросети в строке не нашлось, подставляется наименование от правил.

Правила (`rules`) работают без сети. Бренд это латинское слово с заглавной, модель это токен с
цифрами сразу после бренда, наименование это начало строки до первой запятой, цифры или
латинского слова. Строки формы ЕИС вида «Имя: значение Имя: значение» разбираются на пары по
двоеточиям (`named_pairs`): имя следующей характеристики начинается с русского слова с
заглавной, «Единица измерения товара: Штука» идёт в `measure`, а пояснение «(25,4 мм)» после
дюймов выбрасывается. В остальных строках характеристики ищет регулярное выражение «название,
число, единица»; «не менее», «более» остаются частью значения («белизна: не менее 146 %»).
Причина, по которой пришлось использовать правила, записывается в `attributes.fallback` и
показывается пользователю: `no_key` (нет ключа), `unavailable` (нейросеть не ответила),
`budget` (кончилось время), `error` (ошибка), `missing` (нейросеть пропустила строку).

Как запрос проходит провайдеров (`ask`, `take_provider`):

1. Берётся первый провайдер из списка, у которого есть ключ, он не на паузе и не пробовался
   для этой пачки. GigaChat берётся только когда не осталось ни одного другого: пока YandexGPT
   просто занят, пачка ждёт его, а не уходит к GigaChat.
2. Если запрос не удался, провайдер получает паузу и пачка уходит следующему. Сетевая ошибка
   без ответа даёт паузу 30 секунд (отказ в соединении 15), 401, 402 и 403 дают 120 секунд,
   429 и 502-504 дают 15 секунд, в течение которых пачки идут к другим.
3. Если ответ обрезан по `max_tokens` (`AnswerCut`), пачка делится пополам и каждая половина
   спрашивается отдельно (`extract_chunk`). Другой провайдер обрезал бы то же самое.
4. Строки, которые модель пропустила в большом ответе, спрашиваются повторно отдельной
   маленькой пачкой.
5. Если все провайдеры не справились или кончился бюджет `LLM_BUDGET` (240 секунд), оставшиеся
   строки получают атрибуты от правил.

`JobExtractor` держит в пуле потоков не больше двух кругов пачек (`AHEAD_ROUNDS`), чтобы другое
задание, загруженное в это время, не ждало весь большой файл. Пул `_pool` общий для всех заданий
и для второго мнения, потоков в нём столько, сколько слотов у всех провайдеров.

### providers.py

Настройки и запрос к одной нейросети.

- `Provider`: имя, тип (`yandex` или `gigachat`; другие имена в `LLM_PROVIDERS` пропускаются с
  предупреждением в логе), адрес, ключ, модель, каталог Yandex Cloud `folder`, лимит ответа `max_tokens`, число
  одновременных запросов (семафор `slots`), лимит запросов в минуту `rpm`, моменты
  `down_until` и `busy_until` (паузы).
- `load()` читает `LLM_PROVIDERS` и для каждого имени собирает `Provider` из переменных
  окружения. `yandex()` собирает адрес модели `gpt://<каталог>/<модель>`; запрос к Яндексу идёт
  с заголовками `Authorization: Api-Key <ключ>` и `OpenAI-Project: <каталог>`. `setting()` для
  имён с номером на конце (`yandex2`) берёт недостающие значения из блока без номера
  (`YANDEX_*`), поэтому для нового ключа достаточно одной строки `YANDEXn_API_KEY`.
- `chat()` делает запрос с двумя повторами на 429, 5xx и молчащую сеть. Ответ 5xx, пришедший
  позже 15 секунд, считается молчанием шлюза и повторов не получает.
- `wait_turn()` растягивает запросы провайдера во времени на 60/RPM секунд, чтобы бесплатный
  тариф не отвечал 429.
- GigaChat выдаёт токен на 30 минут через OAuth, он кэшируется (`access_token`) и обновляется
  за минуту до конца. Сертификаты GigaChat выданы российским корневым центром, которого нет в
  обычных хранилищах, поэтому по умолчанию проверка выключена (`GIGACHAT_VERIFY_SSL=false`).
  Её можно оставить включённой, указав путь к файлу `.pem`.
- Температура `0.0001`: так ответы воспроизводимы.

### embedder.py

`embed(texts)` отправляет тексты в Yandex AI Studio (`foundationModels/v1/textEmbedding`,
модель `text-search-query`), по одному тексту в запросе, четырьмя потоками, не чаще
`YANDEX_EMBED_RPS` запросов в секунду на все потоки, и нормирует векторы. 429 и 5xx повторяются
до четырёх раз (0,5–4 секунды). Таймаут запроса 20 секунд: короткий текст отвечает за 0,1–0,3 с.
`yandex_vectors(texts, model)` нужен `scripts/embed_catalog.py` для каталога (модель
`text-search-doc`). Одинаковые тексты спрашиваются один раз и кэшируются между заданиями (до 50
тысяч записей). Если ключа нет, сервис недоступен или ответ неверный, функция возвращает `None`,
и поиск работает только по словам: такие строки помечаются `attributes.words_only`, получают
низкую уверенность и никогда не уходят в авто.

`state()` отдаёт для `/api/health` состояние `on`, `off` (ключ не задан, в сеть не ходим),
`down` или `unknown`. Последний ответ запоминается при каждом запросе задания; если он старше 30
секунд, `state()` сам спрашивает сервис (таймаут 5 секунд, одновременно только один такой
запрос). Если запрос провисел весь таймаут, следующие 30 секунд пачки идут сразу по словам; после
401 или 403 (ключ отклонён, нет роли в каталоге) так же 120 секунд, а не запрос на каждую пачку.

### search.py

Каталог в памяти и поиск кандидатов. Класс `Catalog` держит матрицу векторов и списки метаданных:
коды, статусы, названия, ОКПД2, слова, характеристики, числовые границы, «неизменяемые
заказчиком» значения, признак «шаблон группы», единицы.

`Catalog.search(vectors, texts, include_inactive, units, column_units, anchors)` для каждой строки:

1. Считает косинус с каждым кодом и берёт 50 ближайших (`_nearest_by_vectors`). Недействующие
   коды отбрасываются, если пользователь не включил «Включать в подбор недействующие коды».
2. Добавляет до 20 кодов по BM25 над основами слов в названии кода (`_lexical`). Код, у которого
   название совпало со строкой, попадёт в кандидаты, даже если вектор был не среди ближайших.
3. Каждому кандидату считает оценку в `_rank`: косинус плюс поправки. Поправки задают
   константы в начале файла.

| Константа                                              | Что делает                                                                                                                                                                                                                           |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WORD_BONUS` 0,02                                             | за каждое слово, общее у строки и кода (числа не считаются)                                                                                                                                     |
| `NUMERIC_BONUS`, `NUMERIC_CLASH` 0,01                       | числовые границы строки совпали с границами кода или легли на другую сторону                                                                                                 |
| `FIXED_BONUS` 0,02, `FIXED_CLASH` 0,04, `FIXED_FLAG` 0,03 | значения «неизменяемых» характеристик кода написаны в строке, противоречат ей, или у кода есть особое «Да», которого в строке нет |
| `TEMPLATE_PENALTY` 0,015                                      | общий код-шаблон группы чуть ниже конкретного                                                                                                                                                          |
| `NAME_EXTRA_PENALTY` 0,01                                     | за каждое слово названия кода, которого нет в строке                                                                                                                                               |
| `UNNAMED_PENALTY` 0,02                                        | за каждую характеристику кода, которую строка не называет                                                                                                                                    |
| `UNIT_BONUS` 0,005, `COLUMN_UNIT_BONUS` 0,03                | единица совпала с догадкой нейросети или с колонкой «Ед. изм.» файла                                                                                                                  |

4. Сортирует и оставляет пять лучших. Каждый кандидат отдаётся с названием, ОКПД2, статусом,
   характеристиками, оценкой `score` (обрезана до 1,0 для показа), полной суммой `raw_score`
   (из неё считается разрыв для уверенности), косинусом, общими словами и совпавшими
   характеристиками.
5. Проверяет, не потерялся ли товар, который строка называет (`_anchored`, «якоря», идея
   Жени из ветки `codex/evening-audit-2026-10-28`). `anchors` — строки файла как их написал
   заказчик. Если начало строки — название из каталога, а у лучшего кандидата нет его слов,
   вместо пятёрки ранжируются коды этого названия, с настоящими косинусами и теми же
   поправками. Лучший кандидат остаётся, если это тот же товар (`same_product`): те же слова в
   любом порядке («Опорный поручень» для «Поручень опорный») или более конкретное название,
   которое начинается с названия строки («Анализатор биохимический метаболического профиля» для
   «Анализатор биохимический»). «3D-сканер стационарный» для «Сканер» не остаётся: слово то же,
   товар другой (на трёх наборах ответов нейросети испорчено 0 строк). Название берётся из
   строки, а не из подсказки нейросети в начале запроса: иначе «Изделия сухарные» превращались
   в «Сухари», «Головные уборы. Вид изделия Шапка» в «Шапку». Замер 28.10.2026 на сохранённых
   ответах нейросети: исправлено 18 строк, испорчено 0, на 1000 строках неверных в авто 10 → 7.

Числа сравниваются в базовых единицах и только внутри одной величины: длина, масса, объём,
память, штуки, проценты, дюймы (`unit_of`, `same_quantity`). «16 ГБ» памяти не попадает в
диапазон «≥ 14 Штука» ядер процессора, «15,6 дюйма» не сравнивается с миллиметрами. Строгая
граница кода («> 1») не включает само число. Число без единицы сравнивается с чем угодно, как
раньше. Десятичное число — одно слово: «2,5 процента» это `2.5`, а не «2» и «5» (раньше значение
«2» или «≥ 2» другого кода считалось написанным в строке). Если меняете `words()`, поднимите
`CACHE_VERSION`: слова кодов лежат в кэше каталога.

Основы слов названий и значений каталога кэшируются (`catalog_stems`, `catalog_words`): одни и те
же несколько тысяч строк встречаются у каждой позиции, и без кэша ранжирование 1000 строк
занимало 7,7 секунды вместо 2,4.

Обоснования значений констант записаны комментариями рядом с ними: каждое подбиралось по
замерам. Менять их по одной без замера на двух наборах нельзя, одно улучшение легко портит
другое (подробнее в разделе 16).

`load_catalog` читает дамп (`build`) или кэш из `CACHE_DIR`. Ключ кэша состоит из версии
`CACHE_VERSION`, размера и времени изменения дампа. Если поменяете состав метаданных, поднимите
`CACHE_VERSION`, иначе будет использоваться старый кэш. Метод `lookup` ищет код для ручной
правки: по началу кода или по словам названия, действующие коды первыми.

### confidence.py

Из пяти кандидатов делает уверенность в процентах:

```
z = 8.8 * min(оценка_первого, 1) + 123.7 * min(разрыв, 0.2) - 7.78
разрыв = полная_оценка_первого - полная_оценка_второго
уверенность = 100 / (1 + exp(-z))
```

Чем выше оценка первого кандидата и чем дальше он от второго, тем выше уверенность. Коэффициенты
подогнаны логистической регрессией по 4000 строкам (файл на 1000 строк и его изменённая копия, с
нейросетью и без). Разрыв берётся из полных сумм `raw_score`, а не из обрезанных до 1,0: раньше
два соседних кода, оба набравшие больше 1,0, получали разрыв 0 и уверенность 94 % при любом
настоящем разрыве, и 6 % таких строк были с неверным кодом. Старые позиции, сохранённые без
`raw_score`, считаются по `score`.

Зоны: от 85 процентов `high`, от 60 `medium`, ниже `low`. Автоматически (`auto`) код
принимается только в зоне `high`, если код действующий и строка похожа на товар. Остальные
позиции получают `needs_review`. Функция `explain` собирает пояснение «почему этот код» из общих
слов, совпавших характеристик и числовых границ, это обычный текст без нейросети.

### chooser.py

Второе мнение по спорным позициям. В нейросеть уходят только позиции `needs_review` с больше чем
одним кандидатом, по пять в запросе. Чтобы не раздувать запрос, кандидатам оставляют только те
характеристики, значения которых различаются (`differing`). Ответ принимается, только если код
есть среди кандидатов этой позиции. Бюджет времени `LLM_CHOOSE_BUDGET` (90 секунд), и никогда не
позже `JOB_TIME_LIMIT`. Выключается переменной `LLM_CHOOSE=0`. Если нейросеть выбрала другой код,
у позиции нет процента («—»): процент поиска относился к другому коду, а процент кандидата в
карточке говорит только, что поиск предпочёл не его (верный «Сканер» показывал 0 % рядом с
неверным «3D-сканером»). Позиция остаётся на проверке, причина: «Нейросеть выбрала этот код…». Согласие нейросети с поиском не повод для авто: на 1000 строках
такие позиции с уверенностью от 60 % верны в 96 случаях из 108.

## 7. База данных

Схема обновляется миграциями Alembic перед запуском обработчиков. Для новой колонки нужна новая миграция; существующая база без версии принимается только после резервной копии и проверки схемы. См. [инструкцию](docs/database-migrations.md).

Таблица `jobs`:

| Поле                                        | Что это                                                                                                   |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `id`                                          | uuid, он же имя файла на диске                                                               |
| `filename`                                    | имя загруженного файла                                                                      |
| `status`                                      | `queued`, `processing`, `done`, `failed`, `cancelled`                                                 |
| `total`, `processed`                        | сколько строк в файле и сколько готово                                          |
| `error`                                       | текст ошибки для пользователя                                                         |
| `include_inactive`                            | учитывать ли недействующие коды                                                     |
| `created_at`, `started_at`, `finished_at` | время                                                                                                      |
| `stage_seconds`                               | JSON: секунды по этапам `read`, `extract`, `search`, `confidence`, `choose`, `total` |

Таблица `items`:

| Поле                           | Что это                                                                                                                                                                                                                                                          |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`, `job_id`, `row_number` | позиция, задание (внешний ключ с каскадным удалением), номер строки файла                                                                                                                                  |
| `raw_text`                       | текст строки, ушедший в нейросеть                                                                                                                                                                                                          |
| `attributes`                     | JSON: `name`, `brand`, `model`, `characteristics`, `search_text`, `measure`, `source` (`llm`, `rules` или `manual`), `provider`, `fallback`, `columns` (исходные колонки), `original` (снимок для отката) |
| `candidates`                     | JSON: пять кандидатов, каждый со своими характеристиками                                                                                                                                                                   |
| `ktru_code`, `ktru_name`       | выбранный код и его название                                                                                                                                                                                                                   |
| `confidence`, `zone`           | уверенность и зона                                                                                                                                                                                                                                     |
| `status`                         | `auto`, `needs_review`, `corrected`, `accepted`, `failed`                                                                                                                                                                                                    |
| `summary`                        | пояснение «почему этот код»; в `attributes` ещё `review` (почему позиция на проверке) и `remembered` (код взят из решения человека)                                                                                                                                                                                                                    |

Как меняется статус позиции:

```
обработка           -> auto или needs_review      (confidence.assess)
accept              -> accepted
ручной код (PATCH)  -> corrected
правка атрибутов    -> corrected                  (код подобран заново, человек строку видел)
undo-code           -> код и статус до последней ручной смены
revert              -> то, что было до accept, PATCH или правки атрибутов
ошибка на строке    -> failed
```

Таблица `decisions` (память решений): `key` (sha256 текста строки без учёта регистра, пробелов
и «ё»), `job_id`, `ktru_code`, `ktru_name`, `decided_at`. Запись появляется, когда человек ставит
код вручную или принимает спорную позицию; та же строка в следующих файлах сразу получает этот код
(статус `auto`, уверенность не придумывается, в списке подпись «Код из решения человека»).
«Вернуть на проверку», «Вернуть предыдущий код» и удаление задания убирают его решения.
`REMEMBER_DECISIONS=0` выключает память; для замеров на файлах, которые уже кто-то исправлял,
её лучше выключить. Таблица решений создаётся начальной миграцией Alembic.

Индексы стоят на `items.job_id`, `items.status` и `jobs.status`. Удалить задание можно кнопкой на
сайте; с `JOBS_KEEP_DAYS=N` законченные задания старше N дней удаляются сами раз в час (решения
людей при этом остаются). По замеру 23 октября 33 тысячи
позиций занимали в базе около 95 МБ.

### Как устроено состояние

Глобального хранилища нет. Каждый экран сам запрашивает данные и держит их в `useState`.

- `JobScreen` опрашивает `GET /api/jobs/<id>` раз в секунду, пока задание в очереди или идёт.
  В ответе есть `counts`, по ним `Results` рисует число позиций в каждом статусе.
- `Results` перезапрашивает список, когда меняется `job.processed`, фильтры, поиск, страница или
  счётчик `version` (его увеличивают после массового принятия). Поэтому новые карточки
  появляются сами. Поиск откладывается на 300 мс, чтобы не слать запрос на каждую букву.
- `ItemScreen` держит позицию вместе с соседями (`prev_id`, `next_id`, `next_unreviewed_id`).
  После каждого изменения позиция запрашивается заново.
- Уведомления с кнопкой «Отменить» после «Принять» живут на уровне всего приложения
  (`App` из antd в `App.tsx`), поэтому не пропадают, когда страница переходит к следующей
  позиции.

### Ошибки загрузки

`JobScreen` различает три случая (`loadProblem`): задания нет (404, повторять нечего), ошибка
сервера, нет связи. В двух последних есть кнопка «Повторить»: она убирает ошибку (на экране
появляется заготовка) и делает запрос заново. Кроме того, страница сама повторяет запрос каждые
3 секунды, так что после перезапуска backend она возвращается без нажатий. `ApiError` хранит код ответа в `status`.

цвета (`--ink`, `--accent`, `--primary-bg`, `--green`, `--amber`, `--red` и производные),
размеры (`--text`, `--s1`...`--s8`), скругления. Затем идут блоки по частям интерфейса:
шапка, кнопки, загрузка, плитки, окно прогресса, карточки списка, параметры, страница позиции,
адаптив для узких экранов. Стиль: светлая страница, белые карточки с крупными скруглениями и
мягкими тенями, один синий цвет, шрифт Inter. Тема одна, светлая. Цвета статусов и зон уверенности
всегда сопровождаются словом: у статуса цветная точка и название, у уверенности число.

Настройки antd (`readTokens` в `App.tsx`) читаются из тех же переменных `theme.css`, чтобы поля
ввода и меню выглядели как остальной сайт.

### Тексты

Все надписи лежат в `texts.ts`, объект `T`. Тексты с подстановкой это функции, например
`T.results.pageShown(from, to, total)`. Чтобы поменять надпись, правьте только этот файл.

## 10. Нейросети и ключи

Порядок и список задаёт `LLM_PROVIDERS`. Сейчас это пять ключей YandexGPT (`yandex` и
`yandex2`...`yandex5`, API-ключи сервисных аккаунтов Yandex AI Studio) и GigaChat. YandexGPT
идут первыми, GigaChat запасной: к нему пачка уходит, только когда ни один ключ Яндекса не может
её взять (ошибка, нет ключа, пауза после сбоя).

Как получить ключ Яндекса: в интерфейсе AI Studio кнопка «Создать API-ключ» справа вверху сама
создаёт сервисный аккаунт с нужными ролями и ключ для всех сервисов AI Studio. В `.env` идут
секретная часть ключа (не его идентификатор) и ID каталога (`b1g…`, копируется у названия
каталога вверху экрана). Вручную: сервисный аккаунт с ролью `ai.languageModels.user` или
`ai.editor` в каталоге и API-ключ с областью `yc.ai.languageModels.execute`. Запросы идут в OpenAI-совместимый API
`https://ai.api.cloud.yandex.net/v1`, модель по умолчанию YandexGPT Pro 5.1 (`yandexgpt-5.1`).
Другую модель задаёт `YANDEX_MODEL`, например `aliceai-llm-flash`; YandexGPT Lite 5 снимают с
поддержки 15 ноября 2026.

Облако Яндекса выполняет пять генераций одновременно на все свои ключи вместе: шестой запрос
получает 429 (квота `ai.textGenerationCompletionSessionsCount`, замер 27 октября 2026). Поэтому
пять ключей одного облака работают с `YANDEX_PARALLEL=1`, по одному запросу на ключ: на 292
строках это 69 секунд без единой ошибки, а с `PARALLEL=2` то же время и 11 отказов 429. Ключи из
облаков других аккаунтов добавляют ещё по пять генераций, им нужен свой `YANDEXn_FOLDER_ID` и
`YANDEXn_PARALLEL`. Квоту облака можно поднять через поддержку Yandex Cloud. Ответ ограничен 8000 токенов (`YANDEX_MAX_TOKENS`):
у модели 32 тысячи токенов на вопрос и ответ вместе, пачке из 20 строк хватает 2-4 тысяч.
У GigaChat на бесплатном тарифе один поток (`GIGACHAT_PARALLEL=1`): на второй одновременный
запрос он отвечает 429.

Как добавить ещё один ключ Яндекса: впишите в `.env` строку `YANDEX6_API_KEY=...` (и
`YANDEX6_FOLDER_ID=...`, если ключ из другого облака) и добавьте `yandex6` в `LLM_PROVIDERS`,
потом `docker compose up -d backend`. Остальные значения возьмутся из `YANDEX_*`. Проверка:
`docker compose exec backend python check_llm.py`; при ошибке она печатает код и текст ответа
сервиса.

Других нейросетей нет: в `LLM_PROVIDERS` берутся только `yandex`, `yandexN` и `gigachat`,
остальные имена пропускаются с предупреждением в логе.

Если ключей нет совсем, сайт работает, но атрибуты извлекаются правилами и точность ниже.
Об этом говорят плашка на главной и предупреждение на странице спецификации; причина для каждой
строки хранится в `attributes.fallback`.

## 11. Скорость и узкие места

Требование организаторов: 1000 позиций не дольше 5 минут. Замер 28 октября 2026 (финал): пять
ключей YandexGPT 5.1 (по одному запросу на ключ, облако держит пять генераций на все ключи),
векторы Yandex AI Studio, 20 запросов в секунду. Этапы из `stage_seconds` задания. Подготовка
пачки (ответ нейросети, затем векторы) идёт в отдельном потоке задания, поиск и запись в базу в
основном, поэтому этапы частично идут одновременно и в сумме больше общего времени:

| Этап | 1000 строк | 1000 изм. | human_1000 |
| --- | ---: | ---: | ---: |
| ожидание нейросети (`extract`, поток подготовки) | 139.46 с | 171.41 с | 111.08 с |
| векторы Яндекса (`embed`, поток подготовки) | 72.45 с | 54.63 с | 88.03 с |
| основной поток ждёт готовую пачку (`wait`) | 206.89 с | 221.04 с | 193.6 с |
| поиск по каталогу (`search`) | 3.78 с | 3.58 с | 4.19 с |
| запись в базу (`save`) | 1.21 с | 1.23 с | 1.2 с |
| второе мнение по спорным (`choose`) | 9.41 с | 12.2 с | 15.07 с |
| всего | 221.51 с | 238.36 с | 214.37 с |

До финала векторы пачки запрашивались в том же потоке после ответа нейросети, а следующие пачки
нейросети отправлялись только когда задание просило строку: этап поиска с векторами занимал
35–63 секунды, 1000 строк шли 211–227 секунд. Строк, обработанных правилами, во всех прогонах 0.
Второе мнение успевает: потолок задания `JOB_TIME_LIMIT` 270 секунд.

Где тратится время и что уже сделано:

- Извлечение атрибутов (основная часть, 140–160 с). Определяется скоростью YandexGPT: пять
  запросов одновременно, по 20 строк в запросе, пока одна пачка ждёт ответа, следующие уже
  отправлены, ответ, обрезанный по длине, делится пополам. Шестой одновременный запрос облако
  отклоняет с 429, поэтому `YANDEX_PARALLEL=1`.
- Векторы. Яндекс принимает один текст в запросе, 20 запросов в секунду: тысяча строк это не
  меньше 50 секунд запросов. Они идут в потоке подготовки, пока задание ждёт следующих ответов
  нейросети. Одинаковые тексты не спрашиваются повторно.
- Поиск. Точный косинус по матрице считается пачками по 128 запросов, якоря добавляют меньше
  секунды на 1000 строк.
- Второе мнение (6–13 секунд). Выполняется после всех строк и только для спорных.
- Передача данных. nginx сжимает ответы gzip: скрипт сайта 838 КБ передаётся как 264 КБ.
  Список карточек не отдаёт пять кандидатов (`candidates=false`): ответ на 20 карточек уменьшился
  с 210 КБ до 53 КБ (с gzip около 9 КБ). Список заданий отдаёт готовность каждого задания
  одним запросом, а не сотней. Выгрузка не читает кандидатов из базы.
- Интерфейс получает готовые строки по мере обработки, пользователь работает с ними, не ожидая
  конца.

Что проверено и отброшено. Локальный разбор строк «название из каталога. Поле: значение» без
нейросети (`LLM_LOCAL_STRUCTURED` из ветки Жени) снимает с нейросети 856 строк из 1000, но с
YandexGPT точный код падает: на 1000 строках 965 → 942, на 292 строках 291 → 287. Более быстрая
модель и меньшие пачки не проверялись: запас до 300 секунд есть, а
каждый вариант стоит полного платного прогона по всем наборам.

## 12. Безопасность

- Вход. Учётные записи в таблице `users`, пароль хранится как scrypt с солью (16 МБ памяти на
  проверку). Сессия — случайный токен в cookie `ktru_session` с `HttpOnly` и `SameSite=Lax`
  (чужой сайт не отправит её в POST-запросе), в базе только SHA-256 токена. Сессия живёт
  `SESSION_HOURS` (12 часов), новый пароль закрывает все сессии пользователя. Пять неверных
  паролей подряд для одного логина с одного адреса закрывают вход на минуту; неизвестный логин
  отвечает так же и так же долго, как неверный пароль. С одного адреса можно завести пять
  учётных записей подряд, дальше минута ожидания. За HTTPS поставьте `COOKIE_SECURE=1`.
- Загрузка. Размер не больше 10 МБ, начало файла должно совпадать с расширением, xlsx и docx
  проверяются на zip-бомбу, число ячеек и страниц ограничено. Файл хранится под uuid.
- Нейросети. Текст строки отправляется как данные, ответ проходит проверку «значение есть в
  исходной строке». Код, выбранный нейросетью, должен быть среди кандидатов.
- Выгрузка. Ячейки, начинающиеся с `=`, `+`, `-`, `@` (в том числе после пробелов или переноса
  строки), получают апостроф: формула в Excel не выполнится.
- nginx. Заголовки `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
  `Permissions-Policy` и `Content-Security-Policy`. Загрузки ограничены 20 в минуту с одного
  адреса. Документация API закрыта для сети, backend открыт наружу только на 127.0.0.1.
- Контейнеры. Backend и nginx работают без прав root.
- Секреты. Ключи только в `.env` (он в `.gitignore`). `/api/health` отдаёт имена провайдеров и
  лимиты, ключи никогда.
- В блоке `/assets/` nginx стоит только `expires`: свой `add_header` внутри `location` отменил бы
  все заголовки безопасности сервера для скриптов и стилей. `index.html` не кэшируется.
- Известная слабость: проверка сертификата GigaChat выключена по умолчанию (в примере Сбера
  так же). Для боевого запуска укажите путь к корневому сертификату в `GIGACHAT_VERIFY_SSL`.

## 15. Скрипты и наборы данных

- `scripts/evaluate.py`: замер точности и времени на работающем сервисе, см. раздел 13. Умеет
  оценить уже готовое задание: `--job <id>`. Строки human_1000 без надёжного кода
  (`label_status`) в точность не входят, для них печатается, сколько ушло в авто.
- Сайт со входом: `bench.py`, `evaluate.py` и `tour-shots.mjs` входят под пользователем из
  `EVAL_LOGIN`/`EVAL_PASSWORD` (для тура `TOUR_LOGIN`/`TOUR_PASSWORD`); заведите для замеров
  отдельного пользователя через `users.py`.
- `scripts/bench.py OUT [наборы]`: все размеченные наборы через сервис, одна строка цифр на набор,
  позиции сохраняются в `OUT/<набор>.json`, задания удаляются. Полный прогон всех наборов — около
  3600 строк запросов к нейросети.
- `scripts/replay.py` (внутри контейнера backend) и `scripts/compare_runs.py`: правку поиска или
  уверенности можно проверить без единого запроса к нейросети. Replay заново считает поиск и
  уверенность на сохранённых ответах нейросети, compare_runs сравнивает два прогона построчно и
  возвращает код 1, если хоть одна строка или набор стали хуже. Порядок команд в начале
  `scripts/replay.py`. Сначала прогоните неизменённый код: он должен совпасть с живым прогоном.
- `scripts/embed_catalog.py`: векторы Яндекса для всего каталога, файл для `CATALOG_VECTORS`
  (раздел «Векторы каталога»).
- `scripts/make_primer.py`: собирает пример `frontend/public/primer.xlsx` и его эталон
  `dataset/primer/primer_reference.jsonl`.
- `scripts/make_dataset.py`: строит файлы-эталоны `*_reference.jsonl` рядом с файлами
  организаторов.
- `scripts/generate_chat_data.py`: генерирует синтетический набор на 1000 строк для проверки
  нагрузки и устойчивости (длинные строки, спецсимволы, текст, похожий на инструкцию для модели).
- `dataset/`: файлы организаторов (1000 и 292 строки, пары «с КТРУ» и «без КТРУ»), форма ЕИС
  с тремя позициями, реальная спецификация продуктов на 12 строк, изменённые копии.
  Описание каждого файла в `dataset/README.md`.
- `eval/`: синтетические наборы, `eval/README.md`.
- `scripts/screenshots.mjs`: скриншоты сайта через Edge (Node 22 и новее).
- `scripts/tour-shots.mjs`: картинки обучения `frontend/public/tour/*.webp`. Загружает пример
  `frontend/public/primer.xlsx`, снимает восемь мест с подсветкой и удаляет своё задание.
  Запуск при работающем `npm run dev` и стеке: `node scripts/tour-shots.mjs`.
- `frontend/public/primer.xlsx`: пример на 11 позиций из файлов организаторов и реальной
  спецификации, записанных как в шаблоне; он же шаблон для скачивания на главной. 10 позиций
  уходят в авто, кефир остаётся на проверке и показывает, почему (два кода «Кефир» различаются
  единицей закупки).

## 16. Типовые правки

Поменять порог автоматического принятия. `HIGH` и `MEDIUM` в `backend/confidence.py`. После
смены прогоните `scripts/evaluate.py` и посмотрите точность зоны `high`.

Поменять формулу уверенности. Коэффициенты `W_SCORE`, `W_MARGIN`, `BIAS` в том же файле.
Их подбирали по замеру, так что меняйте только вместе с новым замером.

Изменить правила ранжирования кодов. Константы в начале `backend/search.py`. Правило такое:
любая правка, которая меняет точность, проверяется до и после на двух наборах сразу (файл
организаторов на 1000 строк и реальная спецификация на 12 строк). Улучшение на одном при
ухудшении на другом не принимается.

Поменять промпт нейросети. `SYSTEM_PROMPT` в `backend/extractor.py` (атрибуты) или в
`backend/chooser.py` (второе мнение). Проверка так же: замер до и после.

Добавить колонку в выгрузку. `EXPORT_HEADER` и `export_rows` в `backend/api.py`. Колонки
исходного файла добавляются автоматически.

Добавить статус позиции. Допишите его в `ITEM_STATUSES` и `STATUS_TEXT` в `api.py`, в
`ItemStatus` в `frontend/src/api.ts`, в `T.itemStatus` в `texts.ts`, в `STATUS_ICONS`,
`STATUS_TONE` и `MARK_ICONS` в `ui.tsx`.

Поменять текст на сайте. Только `frontend/src/texts.ts`.

Поменять цвет или размер. Переменная в `:root` в начале `frontend/src/theme.css`.

Добавить страницу. Адрес и разбор в `router.ts` (`parseRoute`, тип `Route`, `paths`), экран в
новом файле, выбор экрана в функции `page()` в `App.tsx`, пункт меню в шапке, если нужен.

Изменить число строк в файле. `MAX_ITEMS` в `backend/parser.py` и текст в `texts.ts`
(`upload.dropHint`). Учтите, что время обработки растёт почти линейно.

Добавить поле в базу. Измените модель в `api.py`. Миграций нет, поэтому для работающей базы
понадобится либо ручной `ALTER TABLE`, либо новая база (`docker compose down -v`).

Новый ключ или провайдер. Раздел 10.

## 17. С чего начать чтение кода

Если читать впервые, удобен такой порядок.

1. `backend/api.py`, сверху вниз до блока эндпоинтов: модели `Job` и `Item`, `claim_job`,
   `run_job`, `process_batch`. Это скелет всей обработки.
2. `backend/parser.py`, функции `parse_file` и `parse_rows`. Видно, откуда берётся текст строки.
3. `backend/extractor.py`: `SYSTEM_PROMPT`, `accept`, `rules`, `ask`, `JobExtractor`.
4. `backend/providers.py`: `Provider`, `load`, `chat`.
5. `backend/search.py`: `Catalog.search` и `_rank`, константы в начале файла.
6. `backend/confidence.py`: короткий файл, формула и зоны.
7. `frontend/src/App.tsx` и `router.ts`: как выбирается экран.
8. `frontend/src/JobScreen.tsx`, `Results.tsx`, `ItemScreen.tsx`: основные экраны.
9. `frontend/src/api.ts` и `texts.ts`: контракт с backend и все надписи.

Тесты читаются как примеры использования: например `backend/tests/test_cancel.py` показывает,
как поднять приложение с пустой базой и вызвать эндпоинты через `TestClient`.

## 18. Ограничения и что можно улучшить

Ограничения, о которых стоит знать.

- Не больше 1000 позиций и 10 МБ на файл.
- Каталог целиком в памяти backend (около 334 МБ плюс рабочая память), масштабировать backend
  горизонтально неудобно: у каждой копии свой каталог.
- Миграций базы нет, схема создаётся `create_all`.
- Нет авторизации и разделения пользователей: все задания видны всем, кто открыл сайт.
- Задания и позиции удаляются сами, только если задан `JOBS_KEEP_DAYS`.
- Скорость зависит от внешних нейросетей: облако Яндекса выполняет пять генераций одновременно
  на все ключи, GigaChat на бесплатном тарифе отвечает одному потоку.
- Ответы нейросети немного различаются между прогонами даже при одном промпте. Одна строка может
  то попадать, то не попадать в топ-5: молоко реальной спецификации («коровье пастеризованное
  2,5 процента») в одном прогоне получает верный код вторым кандидатом, в другом нет, потому что
  нейросеть по-разному пишет подсказку для поиска. Позиция в обоих случаях уходит на проверку.
- Список заданий показывает до 1000 заданий.

Что можно улучшить после сдачи. Эти пункты меняют устройство проекта, поэтому перед сдачей
их не трогали.

- Вход по логину и паролю уже реализован (scrypt). Все задания пока общие. Возможное развитие — владелец задания, фильтрация по владельцу и разграничение ролей; это потребует новой миграции.
- Миграции и разделение backend выполнены: [структура](docs/backend-structure.md), [работа с базой](docs/database-migrations.md). Дальнейшие изменения схемы оформляются новыми ревизиями Alembic.
- Второе мнение по ходу обработки, а не после всех строк, сознательно не сделано: оно занимает те
  же пять слотов запросов, что извлечение атрибутов, поэтому задание не стало бы короче, а по
  пачкам из 20 строк запросов было бы больше (около 50 вместо 31 на 1000 строк). Сейчас оно
  занимает 7–11 секунд в конце.
- Номера страниц в списке заданий вместо кнопки «Показать ещё».
- Смысловые промахи, которые остаются: «Шприц инъекционный трёхкомпонентный 5 мл с иглой»
  получает «Шприц инсулиновый» (уверенность 20–30 %, позиция уходит на проверку, в авто не
  попадает).
- `Art.tsx` и `assets/logo.png` во фронтенде больше не подключены, их можно удалить.
