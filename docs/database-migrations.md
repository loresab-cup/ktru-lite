# Backend и миграции базы

`api.py` собирает приложение и middleware. Папка `routes/` содержит HTTP-маршруты,
`spec_processing.py` — обработку, `job_store.py` — операции очереди, `celery_tasks.py` — задачи Celery; `app_lifecycle.py` — подготовку каталога и очистку.
Подробная карта — [структура backend](backend-structure.md). `models.py` содержит Job, Item,
Decision; модели авторизации остались в auth.py. `database.py` создаёт единственные
engine/SessionLocal, `runtime.py` хранит настройки и общее состояние.
Формирование CSV/XLSX находится в exporting.py. API сохранён. Текущая архитектура — [Celery + Redis и pgvector](case5-architecture.md).

## Текущая схема

Head: `0006_decision_owners`. Миграция 0005 добавляет гостевые аккаунты;
0006 — владельца и исходный текст запомненного решения, независимо от задания.
Старые решения переносятся только при подтверждённом совпадении ключа и исходной строки;
записи без проверяемого источника остаются без владельца и скрыты от аккаунтов. Миграции 0003/0004 добавляют владельцев заданий и
отдельную историю согласий без присвоения старых данных новым аккаунтам.
Подробнее: [разделение данных и согласия](privacy-and-ownership.md).
Миграция `0002_vectors` создаёт расширение vector и отдельную таблицу
каталога с 256-мерными векторами; бизнес-таблицы 0001 сохраняются. Для PostgreSQL
нужен образ с установленным pgvector. Переход с прежнего Docker-тома и откат —
[case5-migration.md](case5-migration.md).

## Новая база

Установите backend/requirements.txt и задайте DATABASE_URL. Из backend выполните
`python migrate.py`, затем `uvicorn api:app`. В Docker startup приложения
выполняет миграции до запуска обработчиков и приёма запросов. Ошибка схемы
останавливает запуск. PostgreSQL advisory lock сериализует миграции нескольких
экземпляров; SQLite использует BEGIN IMMEDIATE.

## Переход существующей базы

1. Прекратите новые загрузки, дождитесь завершения заданий.
2. Сделайте `pg_dump -U <user> -d <database> -Fc -f backup.dump`.
3. Восстановите копию: `pg_restore --no-owner --no-privileges -d <copy> backup.dump`.
4. Задайте DATABASE_URL копии, выполните `python migrate.py --adopt-legacy`.
5. Проверьте данные и приложение. Только затем повторите переход на рабочей базе.

Проверяется соответствие замороженной миграции 0001: таблицы, колонки, типы,
nullable, PK, FK, уникальность, индексы. Несовместимая схема отклоняется.
UUID и UTC timestamps учитывают особенности отражения SQLite/PostgreSQL.
`stamp` только отмечает версию, `upgrade` выполняет изменения схемы. Команда
перехода ставит именно 0001 после проверки, затем выполняет upgrade head.
Начальная миграция явно описывает таблицы и не зависит от будущих ORM-моделей.

## Новые миграции и восстановление

Из backend: `alembic revision --autogenerate -m "Describe schema change"`.
Вручную проверьте результат: переименования и преобразование данных требуют
решения разработчика. Проверьте на новой базе и копии старой, примените
`python migrate.py`. Секреты берутся из окружения, а не alembic.ini.

Для восстановления разверните dump в отдельную пустую базу, проверьте данные
и переключите DATABASE_URL. Не применяйте разрушительный downgrade рабочей базы.
SQLite копируйте при остановленных писателях или используйте SQLite backup API.
